# ADR 046: HFS 内の請求書エディタ（税抜＋源泉・納品済み CR だけ・過剰請求をサーバーで止める）

- Status: Accepted（2026-10-27 オーナー確認済み。§7 の未決事項はすべて推奨案で確定）
- Date: 2026-10-27
- Related: ADR 026（納品完了日で請求月判定）/ ADR 034（初稿請求 `billing_timing`）/ ADR 037（単価承認）/ ADR 047（請求書 PDF の Drive 自動保存）/ ADR 035（契約主体・`users.business_type`）/ ADR 009（納品時スナップショット）/ ADR 036（`isCreativeOfUser`）/ 振込管理（`utils/payout.js`）
- 置き換え: 旧 ADR 046「請求書テンプレ（スプレッドシート）へ納品済み分を下書き出力」（PR #1202・未マージ）。**方針転換によりスプレッドシート出力は採用しない**（2026-10-27 オーナー決定）。番号 046 はこの ADR が引き継ぐ

## Context

法人化（2026-09-22）に合わせて、メンバーからの請求を **税抜単価＋消費税、源泉徴収あり** の形に変える（旧税込額をそのまま税抜として扱う＝10% 還元。源泉 10.21% とおおむね相殺、2026-10-27 決定）。

今の HFS の請求フローは次のとおりで、新方式に対して足りないものがある。

```
＋ 今月の請求書を作成（modal-gen-invoice）
   └ GET /invoices/preview-items … 当月計上の自分の CR ＋ 単価（resolveCreativeRoleCost）
   └ POST /invoices/generate     … 選んだ CR を invoice_items に（1 CR = コスト種別ごとの行・単価は HFS の値が入る）
請求書（マイページ）→ 修正（modal-edit-invoice / PATCH /invoices/:id）→ 提出（POST /invoices/:id/submit）
   └ 提出時に PDF を Drive の月フォルダへ（ADR 047）→ 振込管理がフォルダの PDF をスキャンして合算
```

| 課題 | 今の挙動 |
|---|---|
| 税の扱い | 内税固定（`total_amount` が税込、PDF は `floor(total×10/11)` を小計と表示）。源泉が無い |
| 未納品の請求 | モーダルで未納品（Dチェック中・クライアントチェック中）も選べる |
| 二重請求 | 同じ CR を別の請求書にも入れられる（サーバーにチェックが無い） |
| 単価 | 最初から HFS 単価が入っている（新方針は「未入力で始めて本人が入れる」） |
| HFS 外の仕事 | 修正画面で行を足せるが理由が要らない |
| 操作性 | 1 行ずつ入力。まとめ入力・貼り付け・キーボード移動が無い |
| 宛名 | 「HARUKA FILM / 高橋聖 様」（ADR 047 の Consequences で保留中） |

スプレッドシートに書き出す案（旧 ADR 046）は、入力は楽になるが **提出後にサーバーで再計算・二重請求チェックができない**（シートの中身を HFS が信用できない）ため、HFS 内で完結するエディタにする。

## Decision

### 1. 画面

**(a) 入口のモーダル（既存の「＋ 今月の請求書を作成」を改修・ボタンは増やさない）**

```
┌ 請求書作成   [2026年▼][10月▼] の請求対象            ☐ 🖼 サムネを表示  × ┐
│ ☑  納品日     ファイル名                                     見る          │
│ ☑  10/03     hertech / 動画編集                              🔗           │
│              hertech_241003_A_15s                                         │
│ ☑  09/28     ACME / LP用動画   [前月・未請求]                  🔗           │
│              acme_lp_0928_v2                                              │
│ ☑  ⏱ 作業時間報告（10月）秘書業 3.27h                                       │
│ ── 未納品（請求できません）───────────────────────────────── │
│ ☐  ―         hertech_241020_B_30s   Dチェック中   （グレー・選択不可）     │
│ ☐  ―         acme_banner_03         クライアントチェック中                  │
├──────────────────────────────────────────────┤
│ 3 件を選択中                                   [請求書を作成する] [キャンセル]│
└──────────────────────────────────────────────┘
```

- 一覧に出すのは **本人担当（`isCreativeOfUser`）× 納品完了（`status='納品'`）× まだどの提出済み請求書にも入っていない** CR。当月納品に加え、**前月以前に納品されて未請求のもの**も出して「前月・未請求」バッジ（遡るのは 3 か月まで・§7-3 で確定）
- 未納品は下にまとめてグレー・**選択不可**、日付は納期ではなく「―」
- 小計（金額）列は出さない（単価はエディタで入れる）。説明文は出さないか 1 行まで
- 「見る」は HFS の CR 詳細（`/haruka.html?creative=<id>`・既存のディープリンク）を別タブで開く
- 「🖼 サムネを表示」は **既定 OFF**・状態は localStorage（端末ごと）。ON のときだけ `<img loading="lazy">` で既存の `/portfolio/thumbnail/:fileId`（サーバー代理・キャッシュ付き）を出す。サムネ ID は `creative_files(id, version, uploaded_at)` から最新版の id 文字列だけを返す（クリエイティブ一覧の `thumb_file_id` と同じ作り）。**base64 列（`screenshot_data_url` / `avatar_url` 等）は select に入れない**（PR #940 の 46MB 事故）。OFF なら今と同じ速さ・見た目
- 「請求書を作成する」で **新方式の下書き**（単価は空）を作り、そのままエディタを開く

**(b) 請求書エディタ（新規・全画面モーダル。既存の修正モーダルは旧方式の請求書用に残す）**

```

│ [参考単価を入れる] [単価をまとめて入力] [＋ HFS外の行] [削除]              │
│ ☐ │ 納品日 │ CR・品目                      │見る│参考単価│税抜単価│数量│金額 │
│ ☐ │ 10/03 │ hertech｜hertech_241003_A(編集)│ 🔗 │  6,000 │[      ]│  1 │     │
│ ☑ │ 09/28 │ ACME｜acme_lp_0928_v2(編集)     │ 🔗 │  8,000 │[ 9,000]│  1 │9,000│ ← 赤：参考単価より高い（理由必須）
│   │       │   理由: [追加修正 2 回分        ]                                   │
│ ☐ │  ―    │ 撮影補助（10/12）  HFS未登録     │    │    ―   │[15,000]│[ 1]│15,000│ ← 理由: [CR 登録なしの現場対応]
│                                    小計（税抜）              24,000           │
│                                    消費税（10%）              2,400           │
│                                    ご請求金額（税込）         26,400           │
│                                    源泉徴収税額（10.21%）    -2,450           │
│                                    差引お振込額              23,950           │
│                                                    [PDF を見る] [提出する]    │
└──────────────────────────────────────────────┘
```

- **1 CR × 役割 = 1 行**（同じ CR で編集とディレクションの両方を担当した場合だけ 2 行。単価が役割ごとに違うため）。**CR 行の数量は 1 固定**（入力欄にしない）
- **税抜単価は空欄で始まり本人が入れる**。横に **参考単価**（本人のその役割の単価＝`resolveCreativeRoleCost`、preview-items と同じ解決。本人の分なので本人に見せてよい）
  - [参考単価を入れる]: 選択行（未選択なら全行の空欄）に参考単価をコピー
  - [単価をまとめて入力]: 選択行に同じ単価を一括入力
  - 入力単価 ＞ 参考単価 の行は赤＋「参考単価より高い」、**理由必須**（既存の `invoice_items.price_change_reason` に保存）。参考単価が 0／不明の行は判定しない
- **[＋ HFS外の行]**: CR に無い仕事を手で追加。品目・単価・数量（手入力可）・**理由必須**。「HFS未登録」と表示（青）
- **[削除]**: 選択行を削除（下書きのみ）
- 操作: Tab / Enter / 矢印でセル移動、Excel・スプレッドシートからの貼り付け（タブ区切りを行×列に展開。単価列なら数値だけ取り込み）、Ctrl+D で上のセルの値をコピー
- **下書き自動保存**: 入力が止まって 1.5 秒で保存（`updated_at` で楽観ロック。別タブで更新されていたら上書きせず再読込を促す）。見出しに「保存済み HH:MM」（JST）
- 色は 3 つだけ: 入力欄＝黄 / 要確認＝赤 / HFS未登録＝青

### 2. 計算（サーバーが正）

```
小計（税抜）      S = Σ 行の税抜金額（CR 行は 単価×1、HFS外の行は 単価×数量）
消費税（10%）     T = floor(S × 10 / 100)
ご請求金額（税込） G = S + T                       → invoices.total_amount（従来どおり「税込の請求額」）
源泉徴収税額      W = 源泉あり ? floor(S × 1021 / 10000) : 0
差引お振込額      P = G − W                       → invoices.payout_amount
```
整数演算で計算する（浮動小数の 1 円ずれ対策・ADR 047 と同じ考え方）。源泉の既定は「あり」。

### 3. 過剰請求の防止（サーバー側で必ず再計算）

保存（自動保存含む）と提出のたびに、サーバーがクライアントの値を信用せず次を確かめる。**提出時に 1 つでも満たさなければ 409 で止め、どの行が何に引っかかったかを返す**（下書き保存は止めずに警告として返す）。

| チェック | 内容 |
|---|---|
| 本人の分 | CR 行は `isCreativeOfUser(creative, issuer)`（担当 or 納品時スナップショット D/P）。発行者は本人固定（admin/秘書の代理発行は従来どおり） |
| 納品済み | `creatives.status = '納品'`（`on_first_draft` 案件は初稿提出済みなら可・§7-1） |
| 二重請求なし | 同じ `(creative_id, cost_type)` が **本人の他の提出済み・承認済み請求書**（`status IN ('submitted','approved')`）に無い。差し戻し・削除された請求書は数えない |
| 数量 | CR 行は 1（それ以外の値は 1 に直して保存） |
| 参考単価 | 提出時に参考単価を **その時点で再計算** して `original_unit_price` に保存し直す。単価 ＞ 参考単価 で `price_change_reason` が空なら止める |
| HFS外の行 | `creative_id IS NULL` の手入力行は `manual_reason` 必須 |
| 金額 | 小計〜差引をサーバーで再計算し、画面から送られた `expected_total` / `expected_payout` と違えば止める（画面の表示と PDF・振込額を必ず一致させる） |
| 単価未入力 | 単価が空（NULL）の行があれば提出できない（0 円で出したいなら 0 を入れる） |

二重請求チェックは `invoice_items(creative_id, cost_type)` のインデックス＋ `invoices(status)` の 1 クエリでまとめて行う（N+1 にしない）。DB 制約（部分一意インデックス）は請求書の status を跨げないため使わない。

### 4. データの持ち方

新テーブルは作らない。既存の `invoices` / `invoice_items` に列を足す（migration は Stage 1）。

| テーブル.列 | 型 | 意味 |
|---|---|---|
| `invoices.tax_mode` | TEXT NOT NULL DEFAULT `'inclusive'`（CHECK `inclusive`/`exclusive`） | **請求書ごとの方式フラグ**。既存行はすべて `inclusive`（内税・今までどおり）。エディタで作る新方式は `exclusive` |
| `invoices.subtotal_amount` | INTEGER | 税抜小計 S（exclusive のみ） |
| `invoices.tax_amount` | INTEGER | 消費税 T（exclusive のみ） |
| `invoices.withholding_enabled` | BOOLEAN | 源泉徴収あり/なし（exclusive のみ・既定 true） |
| `invoices.withholding_amount` | INTEGER | 源泉徴収税額 W（exclusive のみ） |
| `invoices.payout_amount` | INTEGER | 差引お振込額 P（exclusive のみ。inclusive は NULL＝`total_amount` を振込額とみなす） |
| `invoice_items.manual_reason` | TEXT | HFS外の行（`creative_id IS NULL`）の理由 |
| index `invoice_items(creative_id, cost_type) WHERE creative_id IS NOT NULL` | | 二重請求チェック用 |

流用する既存列:
- `invoice_items.unit_price` … 税抜単価。**NULL＝未入力**（新方式の下書きは NULL で作る）
- `invoice_items.original_unit_price` … 参考単価のスナップショット（ADR 037 前からある「HFS の既定単価」と同じ意味）
- `invoice_items.price_change_reason` … 参考単価より高くした理由
- `invoice_items.quantity` / `total_amount` / `cost_type` / `creative_label` / `label` / `sort_order` … 従来どおり
- `invoices.total_amount` … **方式に関係なく「税込のご請求金額」**。分析タブの原価（確定）・粗利は従来どおり `total_amount` を足せばよく、内税/外税が混ざっても意味が変わらない

### 5. 既存の内税請求書との互換

- **方式は請求書ごとに固定**（`tax_mode`）。作成時に決め、後から変えない。過去の請求書・PDF・分析・振込管理の金額は一切変わらない
- 新方式を使い始める月は `system_settings.invoice_exclusive_from`（例 `2026-10`）で切り替え（migration 不要の key-value）。**2026年10月分から（§7-2 で確定）**。それより前の月を対象にした作成は旧方式（今のモーダル→修正画面）のまま
- PDF: `buildInvoicePdfModel` が `tax_mode` で分岐。inclusive は今の描画のまま（宛名も含め変えない）。exclusive は §1(c)
- 振込管理: 新方式の PDF は「差引お振込額」を振り込む。`extractInvoiceAmount` に **「差引お振込額」を最優先**で読むルールを足す（無ければ従来の「ご請求金額」→「合計」）。さらに ADR 047 の PDF には `appProperties.hfs_invoice_id` があるので、HFS 製の PDF は DB の `payout_amount`（inclusive は `total_amount`）を正として使う（PDF 読み取りより確実）
- 振込管理の「差分チェック」（実データ per-unit との突合）は、exclusive は `subtotal_amount`（税抜）と比べる
- 旧方式の下書き（移行月より前に作ったもの）はそのまま修正・提出できる。新方式の請求書を旧修正モーダルで開いた場合はエディタへ回す

### 7. 確定事項（2026-10-27 オーナー決定・旧「未決」はすべて推奨案で確定）

1. **初稿請求案件（`billing_timing='on_first_draft'`・ADR 034）**: 初稿を提出済み（`first_draft_submitted_at` あり）なら「請求可」と扱う。それ以外の案件は従来どおり納品完了（`status='納品'`）のみ請求可
2. **適用開始**: 2026年10月分から（`system_settings.invoice_exclusive_from = '2026-10'` 相当。設定が無い場合も 2026-10 を既定とする）。それより前の月を対象にした作成は旧方式のまま
3. **前月以前の未請求を遡る範囲**: 3 か月（対象月を含めず、その前 3 か月）。旧方式で請求済みかどうかは `invoice_items.creative_id` で判定する（手入力の旧請求は判定できない点は運用で補う）
4. **源泉**: 10.21% 一律で計算。1 回の支払（税抜小計）が 100 万円を超える場合は警告だけ出す（本来の 20.42% 部分は手当てしない）。**法人メンバー（`users.business_type='corporation'`）は既定「源泉なし」**、それ以外は既定「あり」。本人がエディタで切り替え可
5. **時間制（ADR 028）・一式分割（ADR 029）の行**: 金額は従来どおりサーバー計算の固定額のまま「税抜」として扱う（旧税込額を税抜とみなす方針と同じ）
6. **支払期限**: 翌月末

### 追補 2026-10-28（初回利用メンバーの指摘を受けて）

- **遡りは新方式の開始月より前に行かない**: 「前月・未請求」は `max(対象月の 3 か月前, invoice_exclusive_from)` から。旧方式の月（〜2026-09）は PDF・手入力で請求済みのものが多く、`invoice_items` では見分けられないため、3 か月遡ると請求済みが一覧に混ざった（§7-3 の「運用で補う」は実運用で成り立たなかった）。2027-01 分からは元どおり 3 か月遡る。旧方式の月の請求漏れは「HFS外の行」で足す
- **Wチェック担当（`creative_assignments.role='wcheck'`）は請求の役割にしない**: 単価マスタに Wチェックの役割は無く、参考単価 0 の「編集」行として他の人の制作 CR が一覧に出ていた。`issuerCostRoles` で `wcheck` の担当行を無視する（同じ CR で D・P なら D/P 費は従来どおり）。`isCreativeOfUser`（マイ実績と共通）は変えない
- **作成モーダルのサムネは既定 ON・クリックで最新版を大きく表示**: ファイル名が末尾の番号だけ違う案件で取り違えないよう、選ぶ前に中身を確かめられるようにする。OFF にした端末は従来どおり軽い一覧

### 追補 2026-10-29（初回利用メンバーの指摘 その2）

- **一覧に出ない CR を名前で探して足せる**（`GET /invoice-editor/search`）: 一覧は対象月＋新方式の開始月以降の前月だけなので、納品日の登録ずれ等で漏れた CR が見つからず「HFS外の行」で手入力 → 金額を打ち間違える、が起きた。作成モーダルの 🔍 で一覧 0 件のとき（足せるものは 1 件以上のときも）本人の CR を期間を問わずファイル名で探し、請求できるものは一覧に追加、できないものは理由（未納品／提出済みの請求書に入っている／Wチェックのみ／翌月以降の納品）を出す。新方式より前の月の納品は「請求済みでないか確かめて」の注意つきで足せる
- **作成後の下書きにも CR を足せる**（`POST /invoice-editor/:id/items`・エディタの「＋ HFSのCRを追加」）: チェックは下書き作成と同じ（`ieBuildCrRows` を共通化。本人の分・納品済み・二重請求）＋この請求書に既にある (CR, 役割) は足さない。楽観ロックは PUT と同じ `updated_at`
- **検索の表記ゆれ**: 全角/半角・大文字/小文字に加え、ひらがな/カタカナ・空白や `_ - .` などの区切り記号を無視する（`searchNorm` / `matchesSearch`・画面とサーバーで共通）
- **並び順**: 作成モーダルは「納品日が古い順（既定）／新しい順／クライアント名順」（端末ごとに記憶）。選んだ順で下書きの `sort_order` になる。エディタは「並び替え…」で同じ 3 通りに並べ替えて保存（PDF もその順）。CR 行だけ並べ替え、作業時間・一式・HFS外の行は後ろに元の順で

### 追補 2026-11-05（立替経費を実費のまま請求できるようにする）

2026年10月分で、撮影のタクシー代・ガソリン代を「HFS外の行」で入れたメンバーの請求書に消費税 10% と源泉が乗った（3,641 円の実費が 4,005 円の請求になった）。エディタは全明細の合計に消費税と源泉をかける作りで、実費を実費のまま入れる手段が無かった。作業時間報告（ADR 028）の立替経費も §7-5 で「税抜として扱う」としていたため同じだった。

**決定（オーナー決定 2026-11-05）: 立替経費（実費）の行は、消費税を上乗せせず、源泉徴収の対象にも入れない。領収書どおりの金額がそのまま振り込まれる。領収書の提出が前提。**

- **対象の行**（`utils/invoice-editor.js` の `EXPENSE_COST_TYPES`）
  - `cost_type = 'expense'` … エディタの「＋ 立替経費」で足す行。内容（品目）と金額だけ。数量は 1 固定・理由は不要
  - `cost_type = 'hourly_expense'` … 作業時間報告の立替経費（金額はサーバー計算の固定額）。§7-5 の「税抜として扱う」はこの行だけ取り消し、実費扱いにそろえる（時間報酬 `hourly_fee`・一式 `installment_fee` は従来どおり税抜）
- **計算**（§2 の差し替え。E＝立替経費の合計）
  ```
  小計（税抜）      S = Σ 立替経費以外の行
  消費税（10%）     T = floor(S × 10 / 100)
  報酬の税込        G = S + T          → invoices.total_amount（意味は変えない）
  立替経費（実費）  E = Σ 立替経費の行
  ご請求金額        G + E              → 請求書・一覧に出す額
  源泉徴収税額      W = 源泉あり ? floor(S × 1021 / 10000) : 0
  差引お振込額      P = G + E − W      → invoices.payout_amount
  ```
- **列は足さない**。`total_amount` は「報酬の税込」のまま（分析の原価・源泉台帳の支払金額・振込の税込は立替経費を含まない＝ADR 028「経費は売上・粗利に含めない」と同じ向き）。案件収支（`project_cost_entries`・DB トリガーが請求明細を写す）は従来どおり全明細を写すので、立替経費も `cost_type='expense'` の原価として入る（HFS外の行・作業時間報告の立替経費と同じ扱い。トリガー・テーブルに `cost_type` の制約は無い）。立替経費の額は `payout_amount −（total_amount − withholding_amount）` で求める（`expenseOfInvoice`）。PDF・請求書一覧の「ご請求金額」は `total_amount ＋ 立替経費`
- **提出時の合計一致チェック**は、画面の「ご請求金額」（立替経費込み）とサーバーの `grand_total` を比べる
- **PDF**: 立替経費の行は品目に「立替経費（実費）」と出し、合計欄に「立替経費（実費）」の行が増える（立替経費があるときだけ）
- **源泉徴収台帳（ADR 054）**: 税込（支払金額）と源泉は立替経費を含まず、差引支払額だけに立替経費が入る。整合チェックは `税込 ＋ 立替経費 − 源泉 ＝ 差引`
  - 台帳では差引からの逆算を使わない（逆算だと「差引が多い」ズレが全部立替経費に見えて、チェックが効かなくなる）。立替経費の額は **明細（`invoice_items`）の合計** をローダが請求書に付ける（`utils/invoice-expense-source.js`。請求書を取る問い合わせに明細を埋め込む＝追加の往復なし）。請求書一覧も明細の合計を使う。`payout_records.ledger_snapshot` にも同じ値を `expense_amount` として凍結する。この追補より前の snapshot は 0 として扱う
  - 例外は API 振込の明細（`payout_transfer_items`）。立替経費の列が無く、振込額は依頼時に請求書の差引から転記した凍結値なので、`振込額 −（税込 − 源泉）` の正の差を立替経費とする（この経路だけ「差引が多い」ズレを検知できない）。**あおぞら API 振込（`ENABLE_AOZORA_TRANSFER`）を本番で有効にする前に、`payout_transfer_items.expense_amount` を足して依頼時に凍結する**（宿題）
  - 画面の源泉徴収台帳（振込管理の「🧾 源泉徴収」）にも「立替経費」列を出す
  - 支払台帳シートに「立替経費」列を足す（税込 − 源泉 ＋ 立替経費 ＝ 差引 が列で追える）。月次（納付用）・年次（支払調書用）は列を変えず、立替経費があるときだけ「差引支払額には立替経費 N 円を含む」の注記を出す。立替経費だけの請求書（報酬 0）は「支払金額が 0 以下」の要確認にしない
- **クリエイティブを納品から戻したときの下書きの再計算**（`POST /creatives/:id/admin-status`）: 新方式の下書きは `total_amount` だけでなく小計〜差引をまとめて計算し直す（差引とずれると立替経費の逆算も狂うため）
- **エディタの操作**: 「単価をまとめて入力」は立替経費の行を対象にしない（領収書ごとに金額が違う）。Excel からの貼り付けは、開始行で決めた列と同じ名前の欄に入れる（単価の列が立替経費・HFS外の行の「品目」に入らない）
- **過去の請求書は変えない**。2026-11-05 時点で `expense` / `hourly_expense` の明細を持つ請求書・作業時間報告の立替経費は 0 件
- **不採用**: 消費税だけ外して源泉は対象にする案（報酬の一部として払う扱い）。領収書をもらって実費を返す運用と合わないため

## Consequences

- メンバーは「モーダルで選ぶ → 単価を入れる（参考単価ボタンで一発も可）→ 提出」で終わる。PDF は ADR 047 どおり自動で Drive へ
- 未納品・他人の CR・二重請求・数量水増し・理由なしの単価上乗せは、画面ではなくサーバーで止まる
- `invoices.total_amount` の意味（税込の請求額）は変わらないので、分析・既存一覧の集計は手を入れずに済む。振込額だけは `payout_amount` を見る必要がある（振込管理は Stage 4 で対応）
- 旧方式（内税）と新方式が当面並ぶ。PDF・修正画面・振込管理で `tax_mode` の分岐が残る（Stage 5 で新規作成は新方式に一本化）
- 旧 ADR 046 のスプレッドシート出力（PR #1202）は採用しない。#1202 の切り出し（`collectInvoiceCandidateCreatives` / `ensureMemberInvoiceMonthFolder`）は Stage 2 で必要な分だけ取り込む

## Alternatives

- **スプレッドシートに書き出す（旧 ADR 046・PR #1202 と改訂版）**: 入力は楽になるが、提出物（PDF）の中身を HFS が検証できず、二重請求・未納品請求・単価上乗せを止められない。却下（2026-10-27）
- **既存の修正モーダルを改造するだけ**: 1 行ずつのフォームで、まとめ入力・貼り付け・キーボード移動が入れにくい。内税前提の作りと新方式が同じ画面で混ざる。却下（旧方式の請求書用に残す）
- **新テーブル（`member_invoices` 等）を作る**: 振込管理・分析・PDF・承認フローが全部 `invoices` を見ているため、二重管理になる。列追加で方式フラグを持つ方を採用
- **DB の一意制約で二重請求を防ぐ**: 「提出済みの請求書の中で一意」は status が別テーブルにあるため部分一意インデックスで表せない。トリガーは運用・デバッグが重い。サーバーの提出時チェック＋インデックスで足りると判断

## 追補 2026-11-17: 受取人指定つきの単価行（`line_cost.user_id`）を請求書でも見る

- **きっかけ**: 「D費は 1 枚あたり定額・受け取るのは特定の 1 人だけ」という案件。成果物グループの D費の単価行に受取人を指定しても、請求書側（参考単価・役割の判定）は指定を見ておらず、案件のディレクター（納品時スナップショット）や CR のディレクター担当の全員に D費の参考単価が出ていた。作成本数集計（`resolvePayee`）は以前から「指定があればその人だけ」で、請求書とずれていた
- **決定**: 請求書も作成本数集計と同じ扱いにする（D費 / P費 だけ。`utils/pricing.js` の `payeeDesignations`）
  - `resolveCreativeRoleCost` に `userId`（請求者）を渡す。単価行は「本人指定 → 指定なし」の順で採用する
  - **受取人に指定された人**は、案件のディレクターや CR のディレクター担当でなくても、**その CR に関わっていれば**（担当・Wチェック担当など `isCreativeOfUser`）その役割で請求できる（`designatedRoles`）
  - **D費 / P費 がほかの人だけに指定されている CR** では、案件のディレクター（スナップショット）や CR のディレクター担当でも、その役割の行を出さない（`blockedRoles`）。提出時チェックでも `NOT_OWN_ROLE` で止める。別の成果物グループの D費へ探しに行くこともしない
  - 候補一覧・検索・明細の追加・提出時チェック・参考単価の全部で同じ判定（`ieResolvePricing` → `issuerCostRoles` の第 3 引数）。旧方式（`/invoices/preview-items`・`/invoices/generate`）と振込管理の差分チェックも同じ
  - **制作ロール（editor / designer）は変えない**。同じ役割に本人指定の行があればそれを優先するだけで、人別の行しか無いグループ（参加申請 ADR 051 の承認で作られる）でも、ほかの担当者は従来どおり先頭の行の単価になる
- **残る制限**: 受取人に指定されても、その CR に担当（Wチェック含む）として入っていない人は請求の候補に出ない（作成本数集計はグループの全 CR をその人に付ける）。同じ役割に「指定なし」と「本人指定」の両方を置くと集計は両方を足すので、置かない
- **指定の入れ方**: 画面にはまだ受取人を選ぶ欄が無い（`POST /projects/:id/lines/:line_id/costs` の `user_id` は受け付ける）。当面は管理者が API / DB で入れる
- **注意**: 費用台帳同期（ADR 024）の D費は「指定なしの行」だけを見る。受取人指定つきの D費は台帳には出ない


## 追補 2026-11-22: 提出後に直すためのロック解除（差し戻しと分ける・本人へ通知・本人からの申請）

- **きっかけ**: 提出済み（`submitted` / `approved`）の請求書は本人が直せず、直すには管理者の「差戻」しか道が無かった。その差戻は (1) 本人へ何も通知されず、(2) 本人のミスでなくても画面に赤い「差し戻し理由」と出て、(3) 本人から頼む手段がチャットしか無かった
- **決定**（旧方式・新方式どちらのメンバー請求書にも同じ。`invoice_type='client'` は対象外）
  1. **管理者のボタンを 2 つに分ける**: 「🔓 修正のためロックを外す」と「↩︎ 不備で差し戻す」。中の動きは同じ `POST /invoices/:id/reject`（`status='rejected'`・PDF はゴミ箱へ＝ADR 047 のまま）で、body の `kind: 'unlock' | 'reject'` だけが違う。理由は必須（サーバーでも検証）
  2. **列は足さない**。`kind='unlock'` は `rejection_reason` の先頭に固定文言「修正のためロック解除: 」を付けて保存し、読むときに先頭で見分ける（`utils/invoice-unlock.js` の `buildRejectionReason` / `parseRejectionReason`。`/js/invoice-unlock.js` で配信し画面と共有）。固定文言は一度使い始めたら変えない。過去の差し戻し（固定文言なし）は従来どおり差し戻しとして出る
  3. **戻したら本人へ必ず知らせる**: ベル（既存の種別 `invoice`）＋ `notifyMember(..., { privateOnly: true })`（共有ルームには流さない。届かなければ管理者のマイチャットへ転送依頼）。文面は何月分か・理由・「請求書（マイページ）から開いて直し、もう一度提出してください」・リンク（`?page=invoices&invoice=<id>`）。金額は載せない。通知の失敗で API は失敗させない（結果は `notified` で返し、管理者の画面に出す）
  4. **本人の画面**: ロック解除で戻った請求書は、赤い「差し戻し理由」ではなく落ち着いた色で「修正できる状態です」。状態ラベルも「修正できます」。`rejection_reason` の帯は `status='rejected'` のあいだだけ出す（再提出後に古い理由が残って見えていたのも直る）
  5. **本人からの申請**: 提出済み（`submitted` のみ。`approved` は不可）の自分の請求書に「✏️ 提出後に直したい」。`POST /invoices/:id/unlock-request`（本人のみ・理由必須）が管理者のマイチャットへ一報する（誰の・何月分・理由・リンク `?page=invoices&invoice_unlock=<id>` → ロック解除の確認が開く）。**申請の状態は DB に持たない**。管理者が「🔓 修正のためロックを外す」を押すのが承認で、見送るときは何もしない（本人へはチャットで返す）
  6. **連打対策**: 同じ請求書への申請は 10 分に 1 回（プロセス内の Map。再起動で消えるが目的は連打の抑止なので足りる）。画面も押下後はボタンを「⏳ 修正を申請済み」にして無効化（その画面を開いているあいだだけ）。管理者へ送れなかったときは 502 を返して送り直せるようにする
  7. **戻せるのは `submitted` だけ**（条件付き更新）。これまで API は状態を見ていなかったが、画面のボタンは元から `submitted` にしか出ておらず、二重押しで通知が 2 通飛ぶのを防ぐために揃えた。承認済みを戻す操作は今回も作らない（振込管理に載ったあとの扱いが別途要るため）
  8. **振込済み・振込依頼中の月は戻せない**（レビュー指摘で追加）: 同じ本人・年月の `payout_records` が `paid`、または進行中の総合振込（ADR 054。`BLOCKING_BATCH_STATUSES` の依頼に failed / returned 以外の明細がある＝`blockedUserIdsFromItems` と同じ判定）があるメンバー請求書は、戻す操作も本人からの申請も 409 で止める。戻すと PDF がゴミ箱へ行き、請求書が振込管理・源泉徴収台帳の集計から外れて、払った額とずれるため。判定は `utils/invoice-payout-lock.js`（純関数 `payoutLockOf` ＋読み込み `loadInvoicePayoutLock`）。振込のテーブルが無い環境は「該当なし」、それ以外の読み出しエラーは戻さない（500）
  9. **承認も `submitted` だけ**（条件付き更新・それ以外は 409）: 古い一覧の「承認」で、別の画面でロック解除・差し戻しした請求書を承認済みに上書きしないため
  10. **通知文への差し込みは記法を逃がす**: 理由・申請者名・請求書番号の `[` `]` は全角にしてから Chatwork へ（`[To:]` `[toall]` `[info]` を作らせない）、Slack は `&` `<` `>` を逃がす。DB に保存する理由は入力のまま。理由は文字列だけ受け付け、固定文言だけ（本文なし）は不可
  11. **リンクの id は UUID の形だけ使う**（`isInvoiceId`）。管理者へ送れなかったとき（502）も同じ請求書は 1 分だけ送り直しを止める。クライアント宛ての請求書の行は従来どおり「差戻」1 つ（通知なしの文言）
- **権限**: 戻す操作は従来どおり `requireLevel('admin')`。画面のボタンは実効ロールが admin のときだけ出す（`isTopAdmin()`・VIEW AS で admin 以外を見ているあいだは出ない）。申請 API の本人判定は実ユーザー（`req.user.id`）
- **変えないもの**: 金額・明細・源泉・PDF の計算、差し戻し時の PDF ゴミ箱送り、承認（approve）
- **不採用**: `invoices.return_kind` などの列追加（migration と 2 段 PR が要る割に、見分けたいのは表示と通知文面だけ）／申請テーブル（承認待ちの一覧・取り下げ・履歴までは要らない。必要になったら ADR 051 の参加申請と同じ形で足す）／提出済みのまま本人に編集させる（PDF・振込管理スキャンと中身がずれる）

## 追補 2026-11-23: 立替経費の行に日付・支払先・領収書（写真の添付／「領収書なし」の理由）を残す

- **きっかけ**: 立替経費（追補 2026-11-05）は内容と金額しか残らず、領収書はチャットで別に送ってもらっていた。立替を源泉徴収の対象外にできるのは領収書などで実費だと示せる場合なので、証拠を請求書と一緒にシステムに残す（代表者の要望「システム上にデータがあった方がやり取りしやすい」「領収書の写メを入れられる仕掛けが欲しい」）
- **画面**（エディタの「＋ 立替経費」の行。合意した画面どおり）

  ```
  ＋ 立替経費

  │ 内容   [アートホテル撮影 ガソリン代     ]      │
  │ 金額   [1,641] 円                         │

  │ 支払先 [ENEOS ○○店                ]        │

  │           [レシートを紛失したため        ]     │
  └──────────────────────────────────────────┘
    ※ 写真は本人の請求書フォルダ（Drive）に保存
    ※ 「領収書なし」の行は、管理者の画面で目立つ色で表示
  ```
  - ファイル選択は `<input type="file" accept="image/*,application/pdf">`（`capture` は付けない＝スマホでカメラ／写真ライブラリ／ファイルを選べる）。画像は画面側で長辺 2000px の JPEG にしてから送る（HEIC もブラウザが読めれば JPEG に。読めなければ HEIC のまま送る）。PDF はそのまま
  - 金額の入力欄はこの枠の中に置く（立替経費の行の「税抜単価」列は空）。キーボード移動・Ctrl+D・貼り付けは今までどおり列名（`data-col`）で動く
  - 管理者が開いたとき（読み取り専用）は「📎 ファイル名」リンク／「⚠ 領収書なし: 理由」（黄の枠）で出す。管理者の請求書一覧の金額欄にも同じ表示を足す（状態が入っていない行＝この追補より前の請求書は何も出さない）
- **データ**（`invoice_items` に列を足す。新テーブルは作らない・migration は別 PR で先に本番適用）
  | 列 | 型 | 意味 |
  |---|---|---|
  | `expense_date` | DATE | 立替経費の日付 |
  | `expense_payee` | TEXT | 支払先 |
  | `receipt_status` | TEXT（CHECK `attached` / `missing` / NULL） | 写真を添付 / 領収書なし / 未入力 |
  | `receipt_missing_reason` | TEXT | 領収書なしの理由 |
  | `receipt_file_id` / `receipt_file_name` / `receipt_mime_type` / `receipt_uploaded_at` | TEXT / TEXT / TEXT / TIMESTAMPTZ | Drive のファイル ID・名前・種類・保存時刻 |
  - すべて NULL 可・既存行は NULL のまま。対象は `cost_type='expense'` の行だけ。作業時間報告の立替経費（`hourly_expense`）は今回は対象外（列は NULL・検証もしない）
  - 列が本番に無い環境でも落ちない: `ieLoadItems` は列つきで読み、42703 / 「Could not find the … column」なら従来の列で読み直す（`utils/invoice-receipt.js` の `isMissingReceiptColumnError`）。列が無いと分かったら 5 分は従来の列だけで動き、その後もう一度確かめる。列が無いあいだは画面に欄を出さず（`receipt_supported: false`）、提出時にも見ない。一覧・詳細・PDF の select も同じくフォールバックする
- **提出時のチェック**（`lineIssues` / `checkInvoiceForSubmit` に足す。`expenseReceiptIssues`）: 日付（必須・実在する日付）・支払先（必須）・領収書（`attached` ならファイル必須／`missing` なら理由必須／未選択は不可）。欠けていれば 409 で止めてどの行かを返す。**下書きの保存は止めない**（注意として返す）。既存の提出済み・承認済みの請求書には何もしない（遡って検証しない。差し戻し・ロック解除で戻して再提出するときは新しいルールで見る）
  - 保存（PUT）は送られてきた項目だけ書く（古い画面のまま開いていたタブが保存しても、入力済みの日付などを消さない）。日付は `2026/10/25` の形も受け、存在しない日付は 400
- **保存先**: 本人の請求書の月フォルダ（ADR 047 の `member_invoice_folders`・無ければ `ensureInvoiceMonthFolderForUser` で作る）の中に **「領収書」サブフォルダ** を作って置く。振込管理のスキャンはメンバーフォルダ直下のファイルだけを請求書として数える（サブフォルダの中は見ない）ので、領収書の PDF が請求額に合算されることはない
  - ファイル名 `領収書_YYYYMMDD_<内容>_<金額>円.<拡張子>`（日付が未入力なら JST の今日・ファイル名に使えない文字は `_`・内容は 40 文字まで）。`appProperties` に `hfs_kind='invoice_receipt'` / `hfs_invoice_id` / `hfs_item_id`
  - **上書きせず常に新規作成**。差し替え・「領収書なし」への切り替え・行の削除・請求書の削除のときは古いファイルを **ゴミ箱へ**（完全削除しない。共有ドライブでは SA が完全削除できないため）。ゴミ箱送りの失敗は保存・削除を止めない（ログだけ）
  - 種類は **中身の先頭バイトで判定**（JPEG / PNG / HEIC・HEIF / PDF。画面から来た Content-Type や拡張子は信用しない）。1 ファイル 10MB（multer の上限・超えたら 413）。1 行 1 ファイル
  - アップロード API は請求書の `updated_at` を進めない（1.5 秒の自動保存の楽観ロックとぶつけない）。新しい行は先に自動保存して ID を受け取ってから送る
- **API**
  - `POST /invoice-editor/:id/items/:itemId/receipt`（multipart `file`）: 本人 or admin/秘書（`ieLoadInvoiceForAccess`＝既存のエディタと同じ）・下書き／差し戻し中だけ・「＋ 立替経費」の行だけ。列が無い環境は 503 `RECEIPT_NOT_READY`
  - `GET /invoices/:id/items/:itemId/receipt[?download=1]`: Drive からプロキシして返す（**公開リンクは作らない**）。見られるのは本人と、請求書を見られる管理者だけ（`GET /invoices/:id` と同じ `issuer_id === req.user.id || isStaffRequester(req)`。`currentUser.role` / `req.user.role` の直書き比較は足さない・ADR 015）。返す Content-Type は保存時に判定した種類だけ（`nosniff`）
- **PDF**（`utils/invoice-pdf.js`）: 立替経費の品目に「（領収書あり）」「（領収書なし）」を添えるだけ（`receiptNoteOf`）。写真は PDF に入れない
- **変えないもの**: 金額・消費税・源泉の計算（立替経費は今までどおり消費税・源泉の対象外）、`total_amount` の意味、源泉徴収台帳・振込管理
- **不採用**: 写真を Supabase Storage / R2 に置く（請求書の PDF と同じ本人の Drive フォルダにそろえる方が管理者が探しやすい・新しい課金の心配がない）／Drive の公開リンクで見せる（他人に見える）／1 行に複数枚（領収書ごとに 1 行にした方が金額と証拠が 1 対 1 で追える）／`capture="environment"`（カメラしか選べなくなり、PDF やライブラリの写真を付けられない）
- **レビューで足したこと**（PR #1302）
  - **古いタブの自動保存で別の端末の領収書を消さない**: 画面は立替経費の行ごとに「自分が知っている領収書ファイル」（`receipt_file_id`）を送り、サーバーは DB と一致するときだけ領収書の状態・理由を書く（`decideReceiptWrite`）。食い違えばその行の領収書欄は書かず、`receipt_conflicts` と「別の画面で領収書が更新されています。再読み込みしてください」を返す（画面は知らせて読み直す）。さらに書き込みは `receipt_file_id` が読んだときと同じ行だけの条件付き更新にし、0 件なら同じく食い違いとして扱う（ファイルのゴミ箱送りも、書けたときだけ）。ファイルがある行の状態を空に戻す保存は無視する
  - **メンバー一覧の「請求書提出済み」**（`checkFolderHasFiles`）はサブフォルダを数えない（「領収書」フォルダだけの月を提出済みにしない）
  - **一覧（`GET /invoices`）**: 支払先・領収書なしの理由・ファイルの項目は、本人の請求書か admin/秘書のときだけ返す（日付と状態は残す）。一覧 API 自体の権限（他人の請求書一覧が取れる）は既存の問題で、この追補では扱わない
  - アップロードは Drive に置いたあと請求書の状態を読み直し、提出済みになっていたら置いたファイルをゴミ箱へ戻して 409。閲覧は `Content-Security-Policy: sandbox`、リンクは `?v=<file_id>`（差し替え後にキャッシュで古い写真を見せない）。画面はアップロードに失敗したら状態を選ぶ前に戻して保存し直す
  - 詳細・PDF の列なし読み直しは、領収書・登録番号・監査列のうち欠けている列を順に外す（複数欠けていても通る）
- **残る制限**: 「領収書」サブフォルダは初回アップロードで作るので、同じ月に同時に 2 枚送ると同名フォルダが 2 つできることがある（どちらに入っても DB の file_id で見つかる）。同じ行に 2 つの画面からほぼ同時に写真を送ると、後に書いた方が残り、先の方のファイルは Drive に置き去りになる（DB からは参照されない・ゴミ箱にも送られない）。アップロードと提出がほぼ同時だと、提出の判定は直前の状態で行う

## 追補 2026-11-23 その2: 請求書一覧の権限と、領収書の差し替えと提出の競合

- **一覧（`GET /invoices`）**: 本人以外の請求書（全員分・他人の `issuer_id` 指定・クライアント請求書）を返すのは、請求書を見られる管理者だけ（`canListOthersInvoices`＝実ユーザーが admin/秘書（`isStaffRequester`。`GET /invoices/:id` と同じ）**かつ** 実効ロールも admin/秘書）。それ以外の人は `issuer_id` の指定を無視して自分の請求書だけを返す
  - 403 にしない理由: 画面の「請求書（マイページ）」と提出前の読み直しは自分の id を付けて呼ぶので、絞るだけで既存の呼び出しが変わらない。全員分を読むのは管理者の請求書一覧（`invoice.all_view` で出し分け・既定 admin/秘書）だけ
  - VIEW AS: 実ユーザーの判定を必ず通すので権限は上がらない。最高管理者が一般メンバーのプレビュー中は、そのロールと同じく自分の分だけになる（ADR 015 B「絞り込みも実効ロールで」）
  - 二重の守り: 本人でも管理者でもない人に他人の請求書が混ざった場合に備え、立替経費の追補の列（日付・支払先・領収書の状態・理由・ファイル・保存時刻）をすべて外す（`stripPrivateReceiptFields`＝`RECEIPT_COLUMNS` 全部）
  - `GET /invoices/months`（年月ごとの件数だけ）は今回は変えない
- **領収書の差し替えと提出の競合**: アップロードは「請求書が下書き／差し戻し中か」の確認と `invoice_items` の書き込みを、DB 関数 `attach_invoice_item_receipt`（`migrations/2026-11-23b_invoice_item_receipt_attach_fn.sql`）の 1 トランザクションで行う。関数は `invoices` の行を `FOR SHARE` で押さえてから状態を見るので、提出（`invoices` の UPDATE）はアップロードの書き込みが終わるまで待ち、先に提出が確定していればアップロードが `not_editable` → 置いたファイルをゴミ箱へ戻して 409。差し替えでゴミ箱へ送る前のファイルは、関数が書き込む時点で行に入っていたもの（`prev_file_id`）
  - アップロードが先に確定した場合は「提出前の差し替え」で、提出はその内容で行われる（提出の判定は直前に読んだ明細で行うが、写真を付ける変更は判定を厳しくする方向には働かない）
  - 関数が本番にまだ無い（PGRST202 / 42883）あいだは従来の「読み直してから書く」で動く（migration を先に本番適用してからコードをマージする）
  - 関数は SECURITY INVOKER・`search_path` 固定・`anon` / `authenticated` から EXECUTE を外し `service_role` だけに付与
  - **不採用**: migration なしで提出 API 側に条件付き更新を足す案（アップロードは `invoices` を書かないため、`invoices` の 1 行の条件付き更新だけでは「確認」と「別テーブルへの書き込み」の間を閉じられず、書き込み後に状態を見て取り消す方式も、提出がその写真を見て通った場合に取り消してしまう順序が残る）
