# ADR 046: HFS 内の請求書エディタ（税抜＋源泉・納品済み CR だけ・過剰請求をサーバーで止める）

- Status: Accepted（2026-10-27 オーナー確認済み。§7 の未決事項はすべて推奨案で確定）
- Date: 2026-10-27
- Related: ADR 026（納品完了日で請求月判定）/ ADR 034（初稿請求 `billing_timing`）/ ADR 037（単価承認）/ ADR 047（請求書 PDF の Drive 自動保存）/ ADR 035（契約主体・`users.business_type`）/ ADR 009（納品時スナップショット）/ ADR 036（`isCreativeOfUser`）/ 振込管理（`utils/payout.js`）
- 置き換え: 旧 ADR 046「請求書テンプレ（スプレッドシート）へ納品済み分を下書き出力」（PR #1202・未マージ）。**方針転換によりスプレッドシート出力は採用しない**（2026-10-27 オーナー決定）。番号 046 はこの ADR が引き継ぐ

## Context

法人化（2026-09-22）に合わせて、メンバーからの請求を **税抜単価＋消費税、源泉徴収あり** の形に変える（旧税込額をそのまま税抜として扱う＝10% 還元。源泉 10.21% とおおむね相殺、2026-10-27 決定）。

今の HFS の請求フローは次のとおりで、新方式に対して足りないものがある。

```
＋ 今月の請求書を作成（modal-gen-invoice）
   └ GET /invoices/preview-items … 当月計上の自分の CR ＋ 単価（resolveCreativeRoleCost）
   └ POST /invoices/generate     … 選んだ CR を invoice_items に（1 CR = コスト種別ごとの行・単価は HFS の値が入る）
請求書（マイページ）→ 修正（modal-edit-invoice / PATCH /invoices/:id）→ 提出（POST /invoices/:id/submit）
   └ 提出時に PDF を Drive の月フォルダへ（ADR 047）→ 振込管理がフォルダの PDF をスキャンして合算
```

| 課題 | 今の挙動 |
|---|---|
| 税の扱い | 内税固定（`total_amount` が税込、PDF は `floor(total×10/11)` を小計と表示）。源泉が無い |
| 未納品の請求 | モーダルで未納品（Dチェック中・クライアントチェック中）も選べる |
| 二重請求 | 同じ CR を別の請求書にも入れられる（サーバーにチェックが無い） |
| 単価 | 最初から HFS 単価が入っている（新方針は「未入力で始めて本人が入れる」） |
| HFS 外の仕事 | 修正画面で行を足せるが理由が要らない |
| 操作性 | 1 行ずつ入力。まとめ入力・貼り付け・キーボード移動が無い |
| 宛名 | 「HARUKA FILM / 高橋聖 様」（ADR 047 の Consequences で保留中） |

スプレッドシートに書き出す案（旧 ADR 046）は、入力は楽になるが **提出後にサーバーで再計算・二重請求チェックができない**（シートの中身を HFS が信用できない）ため、HFS 内で完結するエディタにする。

## Decision

### 1. 画面

**(a) 入口のモーダル（既存の「＋ 今月の請求書を作成」を改修・ボタンは増やさない）**

```
┌ 請求書作成   [2026年▼][10月▼] の請求対象            ☐ 🖼 サムネを表示  × ┐
│ ☑  納品日     ファイル名                                     見る          │
│ ☑  10/03     hertech / 動画編集                              🔗           │
│              hertech_241003_A_15s                                         │
│ ☑  09/28     ACME / LP用動画   [前月・未請求]                  🔗           │
│              acme_lp_0928_v2                                              │
│ ☑  ⏱ 作業時間報告（10月）秘書業 3.27h                                       │
│ ── 未納品（請求できません）───────────────────────────────── │
│ ☐  ―         hertech_241020_B_30s   Dチェック中   （グレー・選択不可）     │
│ ☐  ―         acme_banner_03         クライアントチェック中                  │
├──────────────────────────────────────────────┤
│ 3 件を選択中                                   [請求書を作成する] [キャンセル]│
└──────────────────────────────────────────────┘
```

- 一覧に出すのは **本人担当（`isCreativeOfUser`）× 納品完了（`status='納品'`）× まだどの提出済み請求書にも入っていない** CR。当月納品に加え、**前月以前に納品されて未請求のもの**も出して「前月・未請求」バッジ（遡るのは 3 か月まで・§7-3 で確定）
- 未納品は下にまとめてグレー・**選択不可**、日付は納期ではなく「―」
- 小計（金額）列は出さない（単価はエディタで入れる）。説明文は出さないか 1 行まで
- 「見る」は HFS の CR 詳細（`/haruka.html?creative=<id>`・既存のディープリンク）を別タブで開く
- 「🖼 サムネを表示」は **既定 OFF**・状態は localStorage（端末ごと）。ON のときだけ `<img loading="lazy">` で既存の `/portfolio/thumbnail/:fileId`（サーバー代理・キャッシュ付き）を出す。サムネ ID は `creative_files(id, version, uploaded_at)` から最新版の id 文字列だけを返す（クリエイティブ一覧の `thumb_file_id` と同じ作り）。**base64 列（`screenshot_data_url` / `avatar_url` 等）は select に入れない**（PR #940 の 46MB 事故）。OFF なら今と同じ速さ・見た目
- 「請求書を作成する」で **新方式の下書き**（単価は空）を作り、そのままエディタを開く

**(b) 請求書エディタ（新規・全画面モーダル。既存の修正モーダルは旧方式の請求書用に残す）**

```

│ [参考単価を入れる] [単価をまとめて入力] [＋ HFS外の行] [削除]              │
│ ☐ │ 納品日 │ CR・品目                      │見る│参考単価│税抜単価│数量│金額 │
│ ☐ │ 10/03 │ hertech｜hertech_241003_A(編集)│ 🔗 │  6,000 │[      ]│  1 │     │
│ ☑ │ 09/28 │ ACME｜acme_lp_0928_v2(編集)     │ 🔗 │  8,000 │[ 9,000]│  1 │9,000│ ← 赤：参考単価より高い（理由必須）
│   │       │   理由: [追加修正 2 回分        ]                                   │
│ ☐ │  ―    │ 撮影補助（10/12）  HFS未登録     │    │    ―   │[15,000]│[ 1]│15,000│ ← 理由: [CR 登録なしの現場対応]
│                                    小計（税抜）              24,000           │
│                                    消費税（10%）              2,400           │
│                                    ご請求金額（税込）         26,400           │
│                                    源泉徴収税額（10.21%）    -2,450           │
│                                    差引お振込額              23,950           │
│                                                    [PDF を見る] [提出する]    │
└──────────────────────────────────────────────┘
```

- **1 CR × 役割 = 1 行**（同じ CR で編集とディレクションの両方を担当した場合だけ 2 行。単価が役割ごとに違うため）。**CR 行の数量は 1 固定**（入力欄にしない）
- **税抜単価は空欄で始まり本人が入れる**。横に **参考単価**（本人のその役割の単価＝`resolveCreativeRoleCost`、preview-items と同じ解決。本人の分なので本人に見せてよい）
  - [参考単価を入れる]: 選択行（未選択なら全行の空欄）に参考単価をコピー
  - [単価をまとめて入力]: 選択行に同じ単価を一括入力
  - 入力単価 ＞ 参考単価 の行は赤＋「参考単価より高い」、**理由必須**（既存の `invoice_items.price_change_reason` に保存）。参考単価が 0／不明の行は判定しない
- **[＋ HFS外の行]**: CR に無い仕事を手で追加。品目・単価・数量（手入力可）・**理由必須**。「HFS未登録」と表示（青）
- **[削除]**: 選択行を削除（下書きのみ）
- 操作: Tab / Enter / 矢印でセル移動、Excel・スプレッドシートからの貼り付け（タブ区切りを行×列に展開。単価列なら数値だけ取り込み）、Ctrl+D で上のセルの値をコピー
- **下書き自動保存**: 入力が止まって 1.5 秒で保存（`updated_at` で楽観ロック。別タブで更新されていたら上書きせず再読込を促す）。見出しに「保存済み HH:MM」（JST）
- 色は 3 つだけ: 入力欄＝黄 / 要確認＝赤 / HFS未登録＝青

### 2. 計算（サーバーが正）

```
小計（税抜）      S = Σ 行の税抜金額（CR 行は 単価×1、HFS外の行は 単価×数量）
消費税（10%）     T = floor(S × 10 / 100)
ご請求金額（税込） G = S + T                       → invoices.total_amount（従来どおり「税込の請求額」）
源泉徴収税額      W = 源泉あり ? floor(S × 1021 / 10000) : 0
差引お振込額      P = G − W                       → invoices.payout_amount
```
整数演算で計算する（浮動小数の 1 円ずれ対策・ADR 047 と同じ考え方）。源泉の既定は「あり」。

### 3. 過剰請求の防止（サーバー側で必ず再計算）

保存（自動保存含む）と提出のたびに、サーバーがクライアントの値を信用せず次を確かめる。**提出時に 1 つでも満たさなければ 409 で止め、どの行が何に引っかかったかを返す**（下書き保存は止めずに警告として返す）。

| チェック | 内容 |
|---|---|
| 本人の分 | CR 行は `isCreativeOfUser(creative, issuer)`（担当 or 納品時スナップショット D/P）。発行者は本人固定（admin/秘書の代理発行は従来どおり） |
| 納品済み | `creatives.status = '納品'`（`on_first_draft` 案件は初稿提出済みなら可・§7-1） |
| 二重請求なし | 同じ `(creative_id, cost_type)` が **本人の他の提出済み・承認済み請求書**（`status IN ('submitted','approved')`）に無い。差し戻し・削除された請求書は数えない |
| 数量 | CR 行は 1（それ以外の値は 1 に直して保存） |
| 参考単価 | 提出時に参考単価を **その時点で再計算** して `original_unit_price` に保存し直す。単価 ＞ 参考単価 で `price_change_reason` が空なら止める |
| HFS外の行 | `creative_id IS NULL` の手入力行は `manual_reason` 必須 |
| 金額 | 小計〜差引をサーバーで再計算し、画面から送られた `expected_total` / `expected_payout` と違えば止める（画面の表示と PDF・振込額を必ず一致させる） |
| 単価未入力 | 単価が空（NULL）の行があれば提出できない（0 円で出したいなら 0 を入れる） |

二重請求チェックは `invoice_items(creative_id, cost_type)` のインデックス＋ `invoices(status)` の 1 クエリでまとめて行う（N+1 にしない）。DB 制約（部分一意インデックス）は請求書の status を跨げないため使わない。

### 4. データの持ち方

新テーブルは作らない。既存の `invoices` / `invoice_items` に列を足す（migration は Stage 1）。

| テーブル.列 | 型 | 意味 |
|---|---|---|
| `invoices.tax_mode` | TEXT NOT NULL DEFAULT `'inclusive'`（CHECK `inclusive`/`exclusive`） | **請求書ごとの方式フラグ**。既存行はすべて `inclusive`（内税・今までどおり）。エディタで作る新方式は `exclusive` |
| `invoices.subtotal_amount` | INTEGER | 税抜小計 S（exclusive のみ） |
| `invoices.tax_amount` | INTEGER | 消費税 T（exclusive のみ） |
| `invoices.withholding_enabled` | BOOLEAN | 源泉徴収あり/なし（exclusive のみ・既定 true） |
| `invoices.withholding_amount` | INTEGER | 源泉徴収税額 W（exclusive のみ） |
| `invoices.payout_amount` | INTEGER | 差引お振込額 P（exclusive のみ。inclusive は NULL＝`total_amount` を振込額とみなす） |
| `invoice_items.manual_reason` | TEXT | HFS外の行（`creative_id IS NULL`）の理由 |
| index `invoice_items(creative_id, cost_type) WHERE creative_id IS NOT NULL` | | 二重請求チェック用 |

流用する既存列:
- `invoice_items.unit_price` … 税抜単価。**NULL＝未入力**（新方式の下書きは NULL で作る）
- `invoice_items.original_unit_price` … 参考単価のスナップショット（ADR 037 前からある「HFS の既定単価」と同じ意味）
- `invoice_items.price_change_reason` … 参考単価より高くした理由
- `invoice_items.quantity` / `total_amount` / `cost_type` / `creative_label` / `label` / `sort_order` … 従来どおり
- `invoices.total_amount` … **方式に関係なく「税込のご請求金額」**。分析タブの原価（確定）・粗利は従来どおり `total_amount` を足せばよく、内税/外税が混ざっても意味が変わらない

### 5. 既存の内税請求書との互換

- **方式は請求書ごとに固定**（`tax_mode`）。作成時に決め、後から変えない。過去の請求書・PDF・分析・振込管理の金額は一切変わらない
- 新方式を使い始める月は `system_settings.invoice_exclusive_from`（例 `2026-10`）で切り替え（migration 不要の key-value）。**2026年10月分から（§7-2 で確定）**。それより前の月を対象にした作成は旧方式（今のモーダル→修正画面）のまま
- PDF: `buildInvoicePdfModel` が `tax_mode` で分岐。inclusive は今の描画のまま（宛名も含め変えない）。exclusive は §1(c)
- 振込管理: 新方式の PDF は「差引お振込額」を振り込む。`extractInvoiceAmount` に **「差引お振込額」を最優先**で読むルールを足す（無ければ従来の「ご請求金額」→「合計」）。さらに ADR 047 の PDF には `appProperties.hfs_invoice_id` があるので、HFS 製の PDF は DB の `payout_amount`（inclusive は `total_amount`）を正として使う（PDF 読み取りより確実）
- 振込管理の「差分チェック」（実データ per-unit との突合）は、exclusive は `subtotal_amount`（税抜）と比べる
- 旧方式の下書き（移行月より前に作ったもの）はそのまま修正・提出できる。新方式の請求書を旧修正モーダルで開いた場合はエディタへ回す

### 7. 確定事項（2026-10-27 オーナー決定・旧「未決」はすべて推奨案で確定）

1. **初稿請求案件（`billing_timing='on_first_draft'`・ADR 034）**: 初稿を提出済み（`first_draft_submitted_at` あり）なら「請求可」と扱う。それ以外の案件は従来どおり納品完了（`status='納品'`）のみ請求可
2. **適用開始**: 2026年10月分から（`system_settings.invoice_exclusive_from = '2026-10'` 相当。設定が無い場合も 2026-10 を既定とする）。それより前の月を対象にした作成は旧方式のまま
3. **前月以前の未請求を遡る範囲**: 3 か月（対象月を含めず、その前 3 か月）。旧方式で請求済みかどうかは `invoice_items.creative_id` で判定する（手入力の旧請求は判定できない点は運用で補う）
4. **源泉**: 10.21% 一律で計算。1 回の支払（税抜小計）が 100 万円を超える場合は警告だけ出す（本来の 20.42% 部分は手当てしない）。**法人メンバー（`users.business_type='corporation'`）は既定「源泉なし」**、それ以外は既定「あり」。本人がエディタで切り替え可
5. **時間制（ADR 028）・一式分割（ADR 029）の行**: 金額は従来どおりサーバー計算の固定額のまま「税抜」として扱う（旧税込額を税抜とみなす方針と同じ）
6. **支払期限**: 翌月末

## Consequences

- メンバーは「モーダルで選ぶ → 単価を入れる（参考単価ボタンで一発も可）→ 提出」で終わる。PDF は ADR 047 どおり自動で Drive へ
- 未納品・他人の CR・二重請求・数量水増し・理由なしの単価上乗せは、画面ではなくサーバーで止まる
- `invoices.total_amount` の意味（税込の請求額）は変わらないので、分析・既存一覧の集計は手を入れずに済む。振込額だけは `payout_amount` を見る必要がある（振込管理は Stage 4 で対応）
- 旧方式（内税）と新方式が当面並ぶ。PDF・修正画面・振込管理で `tax_mode` の分岐が残る（Stage 5 で新規作成は新方式に一本化）
- 旧 ADR 046 のスプレッドシート出力（PR #1202）は採用しない。#1202 の切り出し（`collectInvoiceCandidateCreatives` / `ensureMemberInvoiceMonthFolder`）は Stage 2 で必要な分だけ取り込む

## Alternatives

- **スプレッドシートに書き出す（旧 ADR 046・PR #1202 と改訂版）**: 入力は楽になるが、提出物（PDF）の中身を HFS が検証できず、二重請求・未納品請求・単価上乗せを止められない。却下（2026-10-27）
- **既存の修正モーダルを改造するだけ**: 1 行ずつのフォームで、まとめ入力・貼り付け・キーボード移動が入れにくい。内税前提の作りと新方式が同じ画面で混ざる。却下（旧方式の請求書用に残す）
- **新テーブル（`member_invoices` 等）を作る**: 振込管理・分析・PDF・承認フローが全部 `invoices` を見ているため、二重管理になる。列追加で方式フラグを持つ方を採用
- **DB の一意制約で二重請求を防ぐ**: 「提出済みの請求書の中で一意」は status が別テーブルにあるため部分一意インデックスで表せない。トリガーは運用・デバッグが重い。サーバーの提出時チェック＋インデックスで足りると判断
