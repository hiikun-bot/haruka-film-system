# ADR 040: ホームの最上段は「いま自分にボールがあるもの」にし、ヒーローの数字もボール基準に統一する

- Status: Accepted
- Date: 2026-09-15
- Related: ADR 016（ボール状態）, ADR 032（マイゴール＝本人専用データの前例）, ADR 033（チーム状況＝メンバー間比較を避ける／負荷の集計定義）, ADR 036（マイ実績＝本人専用の実績カード）, ADR 015（VIEW AS チェックリスト）

## Context

ホーム（`#page-dashboard`）は「集計」を出しているが「次の行動」を出していない、という指摘がユーザーからあった（2026-09-15）。実装を確認すると次の状態だった。

| 見る人 | 出ていたもの | 問題 |
|---|---|---|
| editor / designer | ヒーロー「担当中 / 直近3日」＋担当カード一覧（`renderEditorDash`） | クリエイティブ一覧の劣化版で、ホームを開く理由がない |
| director | `renderDirectorDash()` が `renderAdminDash()` をそのまま呼ぶ | コメントには「自チームに絞った」とあるが実際は全社の構成比。自分の管理に使えない |
| admin / secretary / producer | 年月フィルタ＋4グラフ＋3日以内アラート＋予実 | ステータス構成比は「何をすべきか」を示さない |

一方で「いま誰が動かす番か」を表す **ボール保持者**（`getBallHolder()`・ADR 016）は既に全ステータスに定義があり、ADR 033 のチーム状況が `user_ids[]`（複数ホルダー対応）で集計している。ただし ADR 033 は**閲覧を admin＋プロデューサー層に限定**しており、メンバー本人が自分の手番を一覧で見る場所はどこにも無かった。

ADR 032（マイゴール）・ADR 036（マイ実績）で「本人専用データ＝`requireAuth` ＋ `req.user.id` 固定・admin バイパス無し」のパターンが確立しているので、その 3 例目として設計する。

## Decision

1. **`GET /api/haruka/dashboard/my-focus` は `requireAuth` のみ。permission key を作らない。**
   見せる範囲を制御する対象（他人の手番）が存在しないため `role_permissions` に行を足さず、全ロールが自分の分を取得できる。
2. **全クエリを `req.user.id` に固定し、`user_id` パラメータ・admin バイパス・VIEW AS（`X-View-As`）による他人参照は将来も追加しない。**
   コード内コメントに明記。VIEW AS でロールを切り替えても本人の手番が出続けるのは仕様であり、ADR 015 上の権限漏れではない（表示内容が実効ロールに依存しない）。
3. **順位・ランキング・メンバー間比較・他人の数値はこの API／カードから出さない（ADR 033 と整合）。**
4. **指標の定義（JST 固定）。** 集計本体は純関数 `computeMyFocus()`（`utils/my-focus.js`）に置き、routes 側はデータ取得＋ボール解決＋純関数呼び出しのみ。

   | 用語 | 定義 |
   |---|---|
   | 関与CR | 未納品クリエイティブのうち、`creative_assignments` に自分の行がある（**role 問わず**＝editor/designer/director_as_editor/director/producer/wcheck）、または案件の `projects.director_id` / `producer_id` が自分、またはボール保持者が自分 |
   | ボール | `getBallHolder().user_ids[]` に自分が含まれる未納品CR＝「いま自分が動かす番」。`ball_holder_id` キャッシュ列は通知用の単数値（複数ホルダーの先頭しか入らない）ため**使わない**（ADR 033 と同じ） |
   | いま手元 | ボールの件数 |
   | 期限超過 | **関与CR**のうち `final_deadline` < 今日（JST） |
   | 今週締切 | **関与CR**のうち `final_deadline` が今日〜今週日曜（JST・週＝月〜日。`_todayStrJST()` / `_thisSundayStrJST()` を再利用し既存UIと週定義を一致） |
   | クラ確認待ち | 関与CRのうち `getBallHolder().type === 'client'`。制作の手は止まっているので**ボール一覧には出さず**件数だけ別に見せる（ADR 033 と同じ扱い） |

   **ADR 033 との定義差（意図的）**: ADR 033 の「担当」は `ASSIGNEE_ROLES`（editor/designer/director_as_editor）限定だが、本 ADR の「関与CR」は role を問わず案件 D/P も含む。チーム状況は「制作が手元に重複している負荷」を見る画面、ホームは「自分の手番と納期責任」を見る画面で目的が違うため。**同じ人のチーム状況の数字とホームの数字は一致しない**ことを前提とする。
   
   日付は `'YYYY-MM-DD'` の文字列比較と UTC 固定パース（`Date.parse('...T00:00:00Z')`）だけで扱い、`new Date('Y-M-D')` / `getDay()` 等のサーバーローカル依存は使わない。jest で `TZ=UTC` / `TZ=Asia/Tokyo` の両方を通す。

5. **配置（ADR 036 決定6 の配置を改訂）。**
   `#dash-my-focus` を挨拶ヒーロー直下に置き、`#dash-my-stats`（マイ実績）はその下にする。ホームの先頭は「今日、自分が何をするか」＝行動であり、実績はその次という順序にする。`renderMyFocusCard()` は `loadDashboard()` から**全ロール共通**で呼ぶ（マイ実績と違い admin も自分の手番を持つため）。取得失敗時はカードを静かに省略しホームを壊さない。フロントにロール分岐は書かない。
6. **ヒーロー統計（`#dash-hero-stats`）は共通ストア経由で描画する。**
   従来は `renderAdminDash()` / `renderEditorDash()` がそれぞれ `innerHTML` を直接上書きしていたため、非同期の複数ソースが競合して片方の数字が消える。`_dashHeroStats` ストアに部分更新を流し込み、描画順は `renderDashHeroStats()` が一元的に決める（行動系 → 管理系）。`loadDashboard()` の冒頭で `resetDashHeroStats()` を呼び、VIEW AS 切替時に前ロールの数字が残らないようにする（ADR 015）。
   旧 `renderEditorDash()` の「担当中 / 直近3日」は廃止する。`allCreatives`（`GET /creatives` は limit=500・既定で納品除外）由来で取りこぼしがあり、ボール基準の数字と二重に出ると意味が割れるため。
7. **「次にいつボールが来るか」は出さない。**
   ボールゼロのときの空状態は「手元にボールはありません ✨」＋「クライアント確認待ち N件／今週締切 N件」に留める。次の手番が回ってくる時刻はクライアント確認の終わり次第で予測できず、予測値を出すと外れたときに信用を失うため。
8. **パフォーマンス。**
   候補CRは全件走査ではなく「自分に関係しうる3経路」だけを取る（`/my-stats` と同じ取り方）。a) `creative_assignments` に自分（aliased inner join）、b) 自分が D/P の案件、c) **自分が代表ディレクターのチームのメンバーが担当するCR**（`getBallHolder()` のチーム経由フォールバック＝案件に director 未設定でも編集者のチーム代表Dがボールを持つ経路の受け皿）。各経路は PostgREST の既定 max rows（1000行）による silent 打ち切りを避けるため `range` でページングする。c) の `.in()` は URL 長超過事故（PR #919）を避けるためメンバー 200 件で打ち切る（超えた場合は経路 c を諦め、出る件数が減るだけで壊れない）。`users.avatar_url` 等の base64 列は select しない（PR #940）。

## Consequences

- どのロールでログインしても、ホームの先頭に「いま自分が動かす番のもの」が納期順で出る。ホームを開く理由ができる。
- ヒーローの数字がロールによらず「いま手元 / 期限超過 / 今週締切」で揃い、管理層はそれに会社全体の数字（進行中案件 / 本数 / 納品済 / SOS）が続く形になる。
- 同じ人の「チーム状況」と「ホーム」の数字は一致しない（決定4の定義差）。運用時に問い合わせが来たら本 ADR を示す。
- assignments・ステータスの登録が雑なCRは手番が出ない（ADR 033 と同じくデータ整備のインセンティブになる）。
- 新テーブル・migration 無し。既存列（`creative_assignments` / `projects.director_id` / `producer_id` / `final_deadline` / `help_flag`）と既存の `getBallHolder()` だけで成立する。
- `renderDirectorDash()` が `renderAdminDash()` を流用している問題自体は本 ADR では解消しない（Phase 3 の宿題）。ただしディレクターにも自分の Dチェック手番が最上段に出るため、実害は大きく減る。

## Alternatives considered

- **A. チーム状況（`/team-load`）を全ロールに開放し、自分の行だけ見せる**: ADR 033 が「将来『本人にだけ自分の行を見せる』拡張は検討余地あり」としていた案。しかし `/team-load` は全メンバー分を集計する重いクエリで、本人1行のために全社分を回すのは無駄。かつ permission が付いており本人専用データの原則（ADR 032/036）と設計が混ざる。専用エンドポイントにした。
- **B. ADR 033 の「担当」定義（ASSIGNEE_ROLES 限定）をそのまま使う**: ディレクター・プロデューサーが自分の手番も納期責任も一切見られなくなる。ホームの目的（全ロールが自分を管理できる）を満たさないため却下。定義差は明記して受け入れる。
- **C. フロントの `allCreatives` から集計する**: `GET /creatives` は limit=500 かつ既定で納品除外のため取りこぼす（ADR 033 / ADR 036 と同じ理由）。サーバー集計にする。
- **D. 未納品CR全件を取って JS で本人分に絞る（`/team-load` と同じ取り方）**: 実装は簡単だが、1 人のホーム表示のために全社の未納品CRを毎回転送することになる。ホームは全員が毎日開く画面なので、3経路の絞り込みを選んだ。
- **E. 「今日の納期」セクション（`#dash-today`）をマイフォーカスに統合する**: 「今日の納期」は管理層には全社分を見せており役割が違う（納期軸 vs 手番軸）。Phase 1 では両方残し、統合は運用して重複が邪魔になってから判断する。
- **F. ボール一覧から直接ステータスを変更できるようにする**: 遷移の妥当性チェック・納品は `bulk-deliver` 経路必須（#1120）等の制約があり、ホームに簡易版の遷移 UI を作ると二重実装になる。行クリックで既存のクリエイティブ詳細モーダルを開く導線に留めた。
