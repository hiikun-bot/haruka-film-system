# ADR 032: マイゴール（完全個人の目標・タスク管理）は権限機構の外に置き、本人以外は admin も閲覧不可とする

- Status: Accepted
- Date: 2026-08-21
- Related: ADR 003（roles マスタ）, ADR 015（VIEW AS 開発チェックリスト）

## Context

HFS に「🎯 マイゴール」＝個人の目標（例: 法人設立）と、その達成タスク（大分類 → 中分類 → タスクの3階層・100件超規模）を管理するページを追加する。ユーザー要件は次の通り。

- 目標（goal）とタスク（task）は分けて管理し、タスクは目標に紐付け可能
- **完全個人領域**であること。業務データ（案件・請求等）と違い、私的な内容（独立準備・キャリア等）を書くため、**本人以外（admin も）に一切見せない。件数すら見せない**

HFS の既存データはすべて「ロール権限で見せる範囲が変わる共有データ」であり、「誰にも共有されない本人専用データ」はこれが初めてになる。既存の仕組みとの整合を整理する必要がある。

- 権限判定は `role_permissions`（ロール集合 × permission_key）のみで、個人単位の権限付与機構は存在しない
- 全テーブルは RLS を一括 ENABLE 済みだが、サーバーは service_role で接続しており RLS はバイパスされる（＝行レベルの防御はアプリ層の責務）
- VIEW AS（X-View-As）は「実効ロール」を切り替える仕組みで、ログインユーザー本人（`req.user.id`）は変わらない

## Decision

1. **permission key を作らない（全ロール利用可）。**
   このページは「誰かに何かを見せる/操作させる」機能ではなく本人専用メモ帳に近い。見せる範囲を制御する対象が存在しないため、`role_permissions` に行を足さず、ナビも全ロール常時表示にする（`applyRoleBasedUI` の制御対象外）。
2. **アクセス制御は「ログイン本人」のみで行い、admin バイパスを一切設けない。**
   全エンドポイントは `requireAuth` のみ。クエリ条件は常に `req.user.id` を使い、`user_id` パラメータは受け付けない。更新・削除は `.eq('id', id).eq('user_id', req.user.id)` の両方を必須とし、0行なら 404（IDOR 防止。存在の有無すら漏らさない）。`isSuperAdminUser` / admin 判定によるバイパスは**将来も追加しない**（コード内コメントでも明記）。
3. **RLS ポリシーは書かない。プライバシーは100%アプリ層で担保する。**
   サーバーが service_role で RLS をバイパスする現構成では、ポリシーを書いても防御にならず「効いているように見える」誤解を生むだけのため、既存テーブルと同じく一括 ENABLE のままポリシーは追加しない。
4. **集計（進捗率・分類別進捗・今週完了数・ストリーク）はクライアント側で算出する。**
   データ量は本人のタスクのみ（100件規模）で一覧 GET 1本（goals + tasks）に収まるため、サーバー集計の往復を作らない。日付判定（「今週」月〜日・連続日数）は JST 固定とし、純関数を `utils/personal-goals.js`（UMD）に切り出して jest でテストし、同一ファイルを `/js/personal-goals.js` としてフロントに配信して二重実装を避ける。
5. **VIEW AS との関係（ADR 015）。**
   表示内容は実効ロールに依存しないため、VIEW AS で切り替えても本人のデータが出続けるのは仕様（権限漏れではない）。`setPreviewRole` の再描画リストには描画一貫性のため再ロードを追加する。フロントにロール分岐は一切書かない。

## Consequences

- admin であっても他人のマイゴールは API 上一切取得できない（0件と 404 のみ）。運用者がユーザーのデータを代理修復する手段は DB 直接操作のみになる（意図した制約）。
- permission key が無いため、権限管理画面からこのページを「特定ロールに非表示」にすることはできない。そうしたくなった場合は改めて key を追加する（その際も**閲覧できるのは本人のデータのみ**という原則は変えない）。
- 「本人専用データ」のパターン（requireAuth + `req.user.id` 固定・admin バイパス無し）の前例となる。同種の機能（個人メモ等）はこの ADR を参照する。
- Supabase 側の防御が無いため、routes に user_id 条件の抜けが入るとそのまま漏えいになる。レビュー時は本 ADR を参照し「`.eq('user_id', req.user.id)` が全クエリにあるか」を必ず確認する。

## Alternatives considered

- **A. permission key（`my_goals.page` 等）を作り既定 all-allow にする**: 制御したい対象が無く、行が増えるだけ。「権限があるロールは他人の分も見えるのでは」という誤読も誘発するため不採用。
- **B. admin だけは閲覧可にする（既存機能の慣例に合わせる）**: ユーザー要件（管理者含め非公開）に真っ向から反するため不採用。私的な内容を安心して書けることが機能価値の核。
- **C. RLS ポリシー（`user_id = auth.uid()`）で守る**: サーバーは service_role 接続で RLS がバイパスされるため実効性が無い。anon key での直接アクセス経路を作る予定も無く、誤った安心感を生むだけなので不採用。
- **D. 進捗・ストリークをサーバー集計で返す**: データが本人分のみで小さく、集計ロジックの置き場が routes に分散するだけ。クライアント算出＋純関数テストの方が保守しやすいため不採用。

## 追記: 2026-08-22 拡張（term / KPI / priority）

ユーザー要望により同日中に拡張（migrations/2026-08-22_personal_goals_term_kpi.sql）。

- **期間区分 `personal_goals.term`**（short/mid/long・任意）: 短期/中期/長期目標。ヒーローカードは区分順に並び、バッジ表示。
- **KPI `personal_goal_kpis`**: 「何を（title）何回（target_count）する？現在何回（current_count）」の行動KPI。目標に必須紐付け（ON DELETE CASCADE）。＋1ボタンでカウントアップ。
- **タスクの `kpi_id`**（任意・ON DELETE SET NULL）と **`priority`**（high/mid/low・任意）。「担当者」は追加しない（完全個人ツールで担当は常に本人のため、ユーザー提案から意図的に除外）。
- **ライト層への配慮（ユーザー指示）**: KPI・分類・メモ等は目標/タスク両モーダルの `<details>`「詳細設定」にデフォルト折りたたみ。KPIを設定した人のカードにだけKPIバーが出る。タスクは「タスク名＋目標＋クイック期限（今日/明日/今週末）＋優先度」だけの10秒登録を基本線とし、「追加して次を作成」で連続登録できる。
- プライバシー方針は本文と同一（KPI含め全エンドポイント requireAuth＋req.user.id・admin バイパス禁止）。
