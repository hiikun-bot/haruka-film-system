# ADR 035: 作品集の「系統」は業種軸をクライアントに持たせ、表現軸は creative_type から導出する

- Status: Proposed
- Date: 2026-09-01
- Related: 作品ギャラリー（`migrations/2026-07-23_portfolio_gallery.sql` / `2026-07-23_portfolio_favorites.sql`）, ADR 012（カテゴリ別フィールド可視性）, ADR 015（VIEW AS チェックリスト）

## Context

外で知り合った経営者に「ちょっとポートフォリオ見せてよ」と言われる場面がある。そこでは「何系がいいですかね？」という会話が先に立ち、iPhone を見せながら口頭で説明することになる。作品ページには担当者・クライアント・動画/静止画・期間・マイベストの絞り込みはあったが、**「◯◯系」で切る軸が無かった**ため、クライアント名を1社ずつ選び直すしか出せる手が無かった。相手は自社の業種に近い実績を見たいのであって、こちらのクライアント名を知っているわけではない。

「系統」という言葉には 2 つの意味が混ざっている。

1. **業種軸** — 「ビジネス系」「美容系」「教育系」。相手が求めているのはほぼこれ。
2. **表現軸** — 「縦型ショート」「バナー」「実写」「アニメーション」。見せ方の話。

自動振り分けの実現方法も論点だった。ユーザーからは「MacBook 標準の画像判定（Vision framework）のような無料の方法は使えないか」という提案があった。検討した結果、**画像判定も外部 AI API も不要**と判断した。

- 業種の判定材料はサムネイル画像ではなくテキスト（クライアント名・案件名・商材名）であり、対象はクライアント **31 社**しかない。作品 749 件を 1 件ずつ判定する必要がない。
- 表現軸は `creative_type` と納品物の縦横比に既に情報が入っており、機械的に導出できる。
- macOS Vision の汎用分類が返すのは person / text / outdoor 程度の粗いラベルで、「インタビュー系」「UGC 風」の判別はできない。加えてローカル macOS でしか動かず、本番（Railway / Linux）で新規作品を自動判定する用途には使えない。

## Decision

### 1. 業種軸はクライアントが持ち主。作品は例外の上書きだけ持つ

- 値は区分マスターに載せる（`master_categories.code='portfolio_genres'` ＋ `master_items`）。既存の 商材 / 媒体 / FMT / 訴求軸 / サイズ と同じ仕組みなので、設定画面から名称追加・並べ替えができる。削除事故を防ぐため `PROTECTED_CATEGORY_CODES` に登録する。
- 持ち主は `clients.portfolio_genre_code`。**1 社決めればその会社の作品が全部決まる**（31 社 → 749 件）。
- `creatives.portfolio_genre_code` は「この作品だけ別業種」の上書き。NULL＝クライアント継承。ふつうは NULL のまま。
- 初期値は migration 内の UPDATE で投入する。本番の 31 社を案件名・商材・訴求軸から実際に読んで割り当てた。判断がつかなかった 3 社（prima tokyo / ミラリタ / テスト用）は未設定のまま残し、画面の「未設定」チップに集める。

### 2. 表現軸は DB に持たず導出する。作風だけ上書きで足す

- `utils/portfolio-genre.js` の `derivePortfolioStyle(creative_type, orientation)` が `creative_type` と向きから決める（縦型ショート動画 / 正方形動画 / 横型動画 / ロング動画 / バナー / SNS投稿画像 / ストーリーズ / サムネイル / LP・Webサイト …）。
- **自動判定できない作風（実写 / アニメーション・モーショングラフィックス / インタビュー / UGC風 / イラスト）は `auto: false` として定義だけ持ち、自動では絶対に付かない**。付けたい作品にだけ `creatives.portfolio_style_code` で人が上書きする。
- 導出ロジックと値の一覧はコードが正なので、表現軸は区分マスターに載せない（載せると導出ルールとの二重管理になる）。

### 3. チップの件数はクロスファセットで数える

`GET /portfolio` は `genre_facets` / `style_facets` を返す。各ファセットは**もう一方の軸だけを適用した集合**で数える。業種チップを選んだ瞬間に表現チップの件数が 0 だらけになって続けて絞り込めなくなるのを防ぐため。選択中なのに 0 件になった系統は、チップが消えて解除できなくなるのでフロント側で必ず表示する。

### 4. 系統フィルタは保存しない

カードサイズやレーンの畳み状態は localStorage に保存しているが、系統の選択は保存しない。その場の会話で切り替えるものであり、次に開いたときに前回の絞り込みが残っていると「作品が減った」と誤認するため。

### 5. 権限

作品ごとの系統の上書きは、説明文（`portfolio_note`）と同じ `canEditPortfolioNote()`（admin / secretary / 担当者本人 / 案件の director・producer）。クライアントの業種設定は既存のクライアント編集（`project.create_edit`）に相乗りする。新しい permission key は作らない。

### 6. migration 未適用でも壊さない

`GET /portfolio` の select は「系統の列あり」で投げ、`column ... portfolio_genre_code does not exist` を検知したら列なしで引き直す。クライアント保存も既存の `insertOrUpdateClientWithFallback` の列落としフォールバックに乗せる。作品ページが真っ白になるより、系統だけ出ない方がましという判断（PR で列追加とコードが同時に main へ乗るため、Railway デプロイと Supabase 適用の順序が前後しても事故らない）。

## Consequences

- 「何系がいいですかね？」→ チップ 1 タップで見せられる。スマホでは系統行が横スクロールするので、片手で操作しながら説明できる。
- 新しいクライアントを登録したときは業種が未設定になる（「未設定」チップに出る）。クライアント編集で選べば以後の作品に自動で効く。自動推定は行わない＝間違った系統が黙って付くことがない。
- 表現軸は納品物の実寸に依存するので、比率が未解決の作品（Drive 実寸を取りに行く前）は「横型」に寄る。既存のレーン分けと同じ挙動であり、実寸が埋まれば次回から正しくなる。
- 業種区分は 16 個（実データに沿った初期値）。増減は区分マスターから可能だが、**チップが増えるほど「1 タップで出せる」価値が下がる**ので、増やす前に統合を検討する。

## Alternatives

- **作品 749 件を 1 件ずつ AI で分類する**: 外部 API 課金が発生し、しかもクライアントが同じなら業種も同じなので大半が無駄。1 社決めれば済む話を 749 回やることになる。却下。
- **macOS Vision framework でサムネイルを画像分類する**: 無料で動くが、返るラベルが粗く業種は判定できない。本番（Linux）では動かず新規作品に効かない。却下。
- **表現軸も DB に列を持って保存する**: 全作品にバックフィルが必要で、`creative_type` が変わったときに追従しない。導出で十分。
- **系統を projects に持たせる**: 案件は同一クライアントで複数あり、業種はクライアント単位で決まるので、案件に持たせると同じ値を何度も入力することになる。
