# ADR 057: ロール別ダッシュボード（旧 #572「ADR 017 案」）の棚卸しと、残りを次にやる単位に切り直す

- Status: Proposed
- Date: 2026-11-24
- Related: ADR 040（マイフォーカス）, ADR 036（マイ実績）, ADR 041（つぶやきカード）, ADR 042（ディレクターのホーム／新着納品ショーケース追補）, ADR 033（チーム状況＝人単位の負荷は admin＋P層限定）, ADR 032（マイゴール＝本人専用データ）, ADR 037（単価承認カード）, ADR 035（契約バナー）, ADR 015（VIEW AS チェックリスト）, ADR 016（ボール状態）
- Supersedes: PR #572（未マージの設計案「ADR 017 ロール別ダッシュボード」。番号 017 は `017-external-director-projects.md` と衝突していたため、本 ADR で置き換える）

## Context

2026-05-11 に PR #572 で「ロール別ダッシュボード」の設計案（以下「旧案」）を出したが、マージされないまま、
2026-09 にホーム刷新が別の流れ（Phase 1〜3）で進んだ。旧案の考え方の多くは既に別 ADR として実装済みで、
旧案のまま進めると二重実装・既存判断との矛盾が起きる。そこで旧案の各項目を現状（2026-11-24 の `origin/main`）
と照らし合わせ、実現済み・方針変更・未実現 に分け、未実現の部分だけを「次にやる単位」として並べ直す。

旧案の柱は 4 つだった。

1. 自分の仕事を全うするブロック
2. 一つ上の役職の視座を覗けるブロック
3. モチベーションとなる数値
4. ユーザー個別カスタマイズ（`dashboard_widgets` / `role_dashboard_defaults` / `user_dashboard_preferences` の 3 層）

その後のホーム刷新で、次の 3 原則が合意されている（ADR 036 / 040 / 042 の前提）。

- ホームは「今日、自分が何をするか」から始める（一覧の劣化版・構成比グラフで始めない）
- 数字は「量」ではなく「自分の変化」を出す
- 他人と比較させない（順位・メンバー間比較は出さない＝ADR 033 / 036）

### 現在のホーム（`public/haruka.html` `#page-dashboard`・`loadDashboard()`）

```
┌─ 挨拶ヒーロー（挨拶 / 日付 / 名言）───────────────────────┐
│ ヒーロー数字: いま手元 / 期限超過 / 今週締切 （全ロール・ADR 040）│
│             ＋ 管理層のみ 進行中案件 / 本数 / 納品済 / SOS       │
├─ 📖 はじめての方へ（登録14日以内の本人のみ）                  │
├─ 🎯 いま、あなたにボールがあるもの（全ロール・ADR 040）        │
├─ 👥 自チームで気になるもの（案件D/P・チーム代表Dのみ・ADR 042）│
├─ 💭 みんなのつぶやき 最新3件（全ロール・ADR 041）              │
├─ 🏅 マイ実績（editor/designer/director・ADR 036）              │
├─ 🎬 新着納品 1 行導線（全ロール・ADR 042 追補）               │
├─ 📝 契約バナー / 📢 全体連絡 / 💴 単価承認待ち / 🎂 誕生日     │
├─ 📅 今日の納期（管理層のみ）                                  │
└─ 年月フィルタ＋4グラフ＋納期アラート＋予実表                  │
   （admin / secretary / producer / producer_director のみ）     │
```

ロール分岐は `loadDashboard()` の 3 本だけ:
`admin / secretary / producer / producer_director` → `renderAdminDash()`、
`director` → `renderDirectorDash()`（ADR 042 で独立）、それ以外 → `renderEditorDash()`。

## Decision

### 1. 旧案の各項目の判定

#### 実現済み

| 旧案の項目 | 実現した形 | ADR / PR |
|---|---|---|
| 共通ヘッダー（挨拶・日付・名言・お知らせ・誕生日） | 既存のまま全ロール共通 | （旧案以前から） |
| ①「自分の仕事」ブロック：自分がボール保持の作業（全ロール） | 🎯 マイフォーカス。ボール基準（`getBallHolder().user_ids[]`）で全ロールの最上段。ヒーロー数字も「いま手元／期限超過／今週締切」に統一 | ADR 040 / #1172 |
| ①「今週の納期（自分の担当）」・editor の「ボール来てる順」 | マイフォーカス（納期順）＋「他N件」→ クリエイティブ一覧「自分のボール」ビュー。二重表示だった「今日の納期」は管理層のみ、「自分の担当（期限順）」は廃止 | ADR 040 追補 / #1177 |
| director の「自分の案件フォーカス」（全社俯瞰をやめる） | ディレクターのホームから全社グラフ・予実を外し、👥 自チームで気になるもの（SOS／期限超過／今週締切・CR 単位） | ADR 042 / #1179 |
| producer の「担当案件にフォーカス」 | 👥 自チームカードは「案件 D/P かチーム代表 D か」で出るため、案件を持つ P にも同じカードが出る（ロール分岐なし） | ADR 042 決定 4 / #1179 |
| ③ モチベ数値「累積（誇り）」「ピーク（記録更新）」 | 🏅 マイ実績：今月／先月／累計納品、今月初稿、納期遵守率（直近3ヶ月）、今月の👍👏、マイルストーン（累計節目・あとK本・先月超え） | ADR 036 / #1140・#1178 |
| ③ モチベ数値「貢献（社会的承認）」 | 作品への 👏 拍手・💬 ひとこと、マイ実績への合算 | ADR 042 / #1141・#1178 |
| 「みんなの動き」が見える場所 | 💭 みんなのつぶやきカード＋ナビ未読バッジ（割り込まない） | ADR 041 / #1176 |
| Phase 4「今月世に出した作品のサムネ帯」 | 🎬 新着納品ショーケース（直近 7 日・作品ページ先頭のカード＋スライドショー・ホームは 1 行導線・ナビ未見バッジ） | ADR 042 追補 / #1183・#1190・#1193 |
| ロール固有の「行動が要る」カード | 💴 単価承認待ち（`project.pricing_approve` 保持者）、📝 契約バナー（本人宛の依頼があるとき） | ADR 037 / ADR 035 |

#### 方針変更（旧案のままではやらない）

| 旧案の項目 | 変更後の扱い | 理由 |
|---|---|---|
| モチベ数値に「リピート率」「回収率」「年間累計受注額」など金額・会社数字を作り手にも出す | 作り手・ディレクターのホームには金額を出さない。会社の金額は admin（と管理層）の画面に留める | 金額の閲覧は本人＋admin が原則（作業時間の予算 #934/#971 と同じ線）。ADR 036 Alternatives B（会社の数字 vs 自分の比較に読まれる）とも整合させる |
| ランキング系（「上位5件」など） | **人**の順位・人ごとの件数比較は出さない。**案件・CR** を並べるのは可 | ADR 033 / 036 / 042。旧案の「担当案件の粗利ランキング」は案件単位なので残せる（下記 Stage B） |
| ②「一つ上の視座」を全ロールに展開 | 一律展開はしない。金額を含まない視座だけを候補にし、出すかどうかはユーザー判断（Open Questions） | 上の 2 行と衝突する。特に editor → 「全社売上予実ミニカード」は金額の原則に反する |
| ④ ウィジェット制御 3 層（新テーブル 3 つ＋設定画面）を「Stage 0（全ての前提）」にする | 前提にしない。後回し（Stage E）にし、着手前に「本当に要るか」を確認する | Phase 1〜3 はテーブル追加なしで成立した。カード数が少ないうちは、ロール推奨を固定にしても困りごとが出ていない。3 テーブル＋設定 UI は工数に見合う根拠がまだ無い |
| 「1発OK率」「平均修正回数」 | 本人のマイ実績に足す候補として残す（Stage C）。他人と比べる形にはしない | 本人の変化として見せるなら原則に合う。定義（修正ラウンドの数え方）が未確定 |

### 2. 未実現の部分を「次にやる単位」に並べ直す

1 単位＝ 1〜2 PR で完結し、単体でリリースして意味がある大きさにする。上から順に推奨。

| 単位 | 内容 | 対象ロール | 主な前提・注意 |
|---|---|---|---|
| **Stage A（旧 Phase 5）: 管理層ホームの円グラフを「行動が要る山」に置き換える** | `renderAdminDash()` のクリエイティブ／案件ステータス構成比（円グラフ 2 枚）を、件数タイル（期限超過 / 担当未設定 / 納期未設定 / SOS / クラ確認待ちのまま納期超過）＋クリックで該当一覧、に置き換える。売上予実・月別納品・予実表は残す | admin / secretary / producer / producer_director | 定義は ADR 040 の用語（JST・`final_deadline`・`help_flag`・`getBallHolder`）に合わせる。CR 単位の件数のみで人単位は出さない（ADR 033）。全件走査になるので集計はサーバー（`/dashboard/my-focus` と同じくページング） |
| **Stage B: プロデューサーの「担当案件」カード** | 自分が `producer_id` の案件だけの「今月納品本数／遅延」と、案件単位の粗利一覧（上位5件・案件の並びであって人の順位ではない） | producer / producer_director（＋案件 P を持つ admin） | 粗利は金額なので本人が P の案件のみ。粗利の正は ADR 002 の `project_estimate_lines`（status 集計条件も同じ）。VIEW AS で前ロールの金額が残らないよう `setPreviewRole` の再描画リストに入れる（ADR 015） |
| **Stage C: マイ実績に「1発OK率／平均修正回数（本人のみ）」** | `creative_versions`（v0=初稿）から、直近3ヶ月に納品した本人の CR のうち修正なしで納品した割合・平均ラウンド数 | マイ実績が出るロール | ADR 036 の判定（`isCreativeOfUser`）と月判定を再利用。他人との比較・平均は出さない。修正ラウンドの数え方は、往復履歴の snapshot の版番号がステータス遷移とずれる既知の癖（PR #1163 で時刻近接マッチ化）に注意 |
| **Stage D: 秘書（経理ライン）向けカード** | 請求・振込の「行動が要るもの」（未提出の請求書・振込待ち・源泉の納付月）を 1 枚に | secretary（現状は admin が兼ねる） | 2026-09 以降、秘書はチームに不在。実際に担う人が決まるまで優先度は低い。作るなら既存の振込管理（ADR 054）・源泉台帳の集計を流用し、新しい金額計算は書かない |
| **Stage E: ホーム表示のカスタマイズ（旧案の 3 層モデル）** | カードの ON/OFF・並べ替え。まずは「カードを畳む」程度を localStorage（端末単位・ADR 041 の流儀）で試し、足りなければ旧案の DB 3 層へ | 全ロール | 新テーブルを作るなら同 migration で RLS 必須（ADR 048）。🔒ロック表示（上位ロールで見られる項目）を出すかは Open Questions |
| **（整理）sub_producer / sub_director の扱い** | 現在 `loadDashboard()` の分岐に無く、作り手（`renderEditorDash`）扱いに落ちる | sub_* | マイフォーカス・👥自チーム・マイ実績はロール分岐なしで出るので実害は小さい。管理層扱いにするか（今日の納期・グラフを出すか）を決めるだけ。決めたら `isManagerDash` / `showsCharts` の 2 か所を同時に直す |

### 3. 実装時に守ること（全 Stage 共通）

- フロントにロール分岐を増やすときは `effectiveRole()` を使い、ADR 015 のチェックリストを通す。可能なら ADR 042 決定 4 のように「その人が案件 D/P か」などの事実で出し分け、ロール名で分岐しない。
- 本人専用の数字は ADR 032 / 036 / 040 のパターン（`requireAuth`＋`req.user.id` 固定・admin バイパス無し）を踏襲する。
- 日付は JST 固定（`toLocaleDateString('sv-SE', { timeZone: 'Asia/Tokyo' })`・`_jstDiffDays`）。jest は `TZ=UTC` / `TZ=Asia/Tokyo` の両方。
- カードの取得失敗はホームを壊さず静かに省略する。base64 列は select しない（PR #940）。大量 ID の `.in()` は使わない（PR #919）。

## Consequences

- 旧案（#572）は閉じ、ロール別ダッシュボードの「残り」は本 ADR の Stage A〜E を正とする。旧 Phase 4 は新着納品ショーケースで実現済みとして扱い、旧 Phase 5 を Stage A に引き継ぐ。
- 旧案の「Stage 0（ウィジェット DB 基盤が全ての前提）」は撤回する。Stage A〜D は新テーブル無しで進められる。
- 作り手・ディレクターのホームに会社の金額は出ない。旧案の「一つ上の視座」のうち金額を含むものは採らない。
- 本 ADR は設計の棚卸しのみで、コード・DB の変更は無い。各 Stage の着手時に、その Stage の詳細を本 ADR の追補か別 ADR に書く。

## Alternatives considered

- **A. #572 をそのまま番号だけ付け替えてマージする**: Phase 1〜3 で実現・変更済みの内容と矛盾する記述（Stage 0 前提、金額の覗き見、作り手のモチベ数値に回収率等）が正として残ってしまう。却下。
- **B. 旧案を全面的に捨てる**: 秘書向け・プロデューサー向け・1発OK率・カスタマイズなど、まだ有効な論点が失われる。棚卸しして残すことにした。
- **C. 旧案どおりウィジェット 3 層を先に作る**: 今のカード構成で困りごとが出ておらず、3 テーブル＋設定画面の工数に見合う根拠が無い。Stage E に後回し。

## Open Questions（ユーザー判断待ち）

1. 「一つ上の視座」を一部だけ出すか。出すなら金額を含まないものに限る案:
   - 作り手 → 案件全体の進捗（その案件の CR が何本中何本納品か）
   - ディレクター → 担当案件の納期の山場（今週・来週の締切本数）
   出さない場合は、本 ADR の Stage には含めない。
2. Stage A のタイルに「クライアント確認待ちのまま納期超過」を独立項目で出すか（ADR 042 の実データ確認で、ディレクターの期限超過の多くがこれだった）。
3. sub_producer / sub_director のホームを管理層扱いにするか、作り手扱いのままにするか。
4. Stage E で、権限が無い項目を 🔒 で見せる（キャリアの動機づけ）か、見せない（ノイズを減らす）か。
5. Stage B の粗利一覧を producer_director にも出すか（PD は D としても動くため、ホームが長くなる）。
