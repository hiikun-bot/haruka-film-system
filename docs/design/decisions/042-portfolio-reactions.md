# ADR 042: 作品への 👏 拍手と 💬 ひとことは tweets と分離した専用テーブルで持ち、制作担当にだけ通知する

- Status: Accepted
- Date: 2026-09-03
- Related: 作品ギャラリー（`migrations/2026-07-23_portfolio_gallery.sql` / `2026-07-23_portfolio_favorites.sql` / ADR 035）, つぶやきの 5 種リアクション（`tweet_reactions` / `tweet_comments`）, 通知 Phase 1（`notification_logs` / `utils/notification.js`）, ADR 033（チーム状況・メンバー間比較を避ける判断）, ADR 015（VIEW AS チェックリスト）, philosophy.md 4 項, open-questions Q3

## Context

🏆 作品ページは納品作品のギャラリーだが一方通行で、他のメンバーからの反応が付かなかった。作った本人にとって「見てもらえた」「良かったと言ってもらえた」が分かる仕組みが無く、ポートフォリオとして眺めるだけの場所になっていた。

一方、つぶやき（tweets）には 5 種リアクション（👍 ❤️ 👏 😊 😳）と短いコメント、それに伴うベル通知の配線が既にある。同じ体験を作品にも付けたい。

論点は 3 つ。

1. **テーブルをどう持つか** — `tweet_reactions` / `tweet_comments` を `target_type` 付きに拡張して共用するか、死蔵の `posts` 系を復活させるか、専用テーブルを作るか。
2. **誰に通知するか** — つぶやきは投稿者 1 人だが、作品は編集者・デザイナー・ディレクターと複数人で作る。
3. **数字の扱い** — 拍手の数が見えると「誰の作品が一番拍手を集めたか」という比較になり得る。

## Decision

### 1. 専用テーブル `portfolio_reactions` / `portfolio_comments` に分離する（tweets 系とは統合しない）

- philosophy.md 4 項「概念の統合より分離」・open-questions Q3 の判断（統合は急がない）を継続する。
- 見た目は同じ「リアクション」でも、対象（`tweet_id` vs `creative_id`）・ライフサイクル（つぶやきは期限切れで消える／作品はずっと残る）・通知の宛先（投稿者 1 人 vs 制作担当の複数人）が違う。`target_type` 列で共用すると、つぶやき側の期限切れ削除や集計トリガー（`reaction_count` の更新トリガー）が作品側に漏れる。
- `posts` / `post_reactions` は未使用のまま塩漬け（Q3 の (B) 案どおり別途削除）。今回の受け皿にはしない。
- `reaction_type` に CHECK は付けない。許可値は `utils/reactions.js` が正で、DB にも書くと二重管理になる（`tweet_reactions` と同じ流儀）。
- `portfolio_comments` は論理削除（`deleted_at`）。本文は 500 字まで（DB の CHECK とコード側 `PORTFOLIO_COMMENT_MAX` を揃える）。

### 2. リアクションの種類の定義は 1 箇所（`utils/reactions.js`）に集約する

- つぶやきのサーバー側 `TWEET_REACTION_TYPES` とフロント側 `TWEET_REACTIONS` が別々に書かれていたのを、UMD 形式の `utils/reactions.js` に集約し、`server.js` が `/js/reactions.js` で配信する（`utils/personal-goals.js` と同じ方式）。作品側もこの配列を使う。

### 3. 通知の宛先＝その作品の「制作担当」。アクター本人には送らない

- 宛先は `creative_assignments` のうち `editor` / `designer` / `director_as_editor` / `director` と、納品時スナップショット `creatives.delivered_director_ids`。`producer` / `wcheck` はチェック側なので含めない（「作った人に届く」通知にする）。
- **自分の作品にも押せる**（つぶやきと同じ）。ただし通知は自分には飛ばさない。
- リアクションの解除では通知しない。
- 連打・トグル往復対策として、同じ人 × 同じ作品 × 同じ通知種別（`portfolio_reaction` / `portfolio_comment`）は **24 時間に 1 回**に抑える（`notification_logs` の `sender_id` + `meta->>creative_id` + `created_at` で判定）。
- 通知種別は `portfolio_reaction`（👏）/ `portfolio_comment`（💬）。`notification_settings` に `*_enabled` 列を足し、`utils/notification.js` の対応表に登録する（`creative_registered` と同じ手順）。
- 通知のリンクは作品ページのディープリンク `/haruka.html?portfolio=<creative_id>`。ベルから開くと作品タブに切り替わり、該当作品のライトボックスが開く。既定の「自分の作品」フィルタに無ければ一度だけ「全員」に広げて探し直す。

### 4. 順位・ランキング化はしない

- カードとライトボックスに「種別ごとの件数」と「自分が押したか」だけを出す。作品を拍手数で並べ替える・メンバー別に拍手数を集計する・トップ N を出す、といった機能は付けない。
- ADR 033 で「メンバー間比較の材料を作らない」と決めた判断と整合させる。拍手は評価ではなく「見たよ」「良かったよ」の合図として扱う。

### 5. 認可は作品ページと同じ（全ロール）。削除だけ本人 or admin

- 作品ページは全ロール閲覧可なので、リアクション／ひとことの API も `requireAuth` のみ（一覧と同じ）。
- ひとことの削除は本人か admin。admin 判定は `getEffectiveRoleCodes(req)`（ADR 015・`req.user.role` 直書き禁止）。フロントの削除ボタンは API が返す `can_delete` で出し分ける。

## Consequences

- 作品ページで 👏＋ を押すとピッカーが開き、5 種から選べる。押した種別はカード下部にピルで並び、自分のものは強調。もう一度押すと外れる。
- 💬 N をクリックするとカード直下にひとこと欄が開く（ライトボックスでは常時表示）。
- 一覧 API（`GET /portfolio`）は creative ごとの `reactions` / `my_reactions` / `comment_count` を **1 往復で**載せて返す（表示中の creative 集合で `.in()` を 100 件ずつに分割し並列取得。N+1 無し）。migration 未適用の環境ではテーブル無しを検知して集計無しで表示する（作品ページを落とさない）。
- `notification_logs` の行数が増える。同一 (actor, creative, 種別) 24h 抑制で連打分は抑えている。

トレードオフ:
- つぶやきと作品でリアクション UI が 2 系統になる（テーブル分離の帰結）。定義（5 種）だけは共通化した。
- 拍手数が見えること自体は避けられない。ランキング化しないことで「比較の道具」にならないようにしている。

## Alternatives

1. **`tweet_reactions` に `target_type` / `target_id` を足して共用** — テーブル数は減るが、つぶやきの期限切れ削除・件数トリガー・通知の宛先ロジックが作品側に混ざる。philosophy 4 項の「安易な統合は危険」に該当するため見送り。
2. **死蔵の `posts` 系を作品用に転用** — 「統一 feed の試みが頓挫した跡」を別の意味で再利用すると、後で読む人が混乱する。見送り。
3. **通知の宛先を「案件の director_id / producer_id」まで広げる** — 案件のディレクターは複数の作品にまたがるため、作品ごとの拍手が全部届くと多すぎる。作品単位の担当（creative_assignments）と納品時スナップショットに限定。
4. **拍手ランキング / 月間ベスト** — モチベーション施策としては考えられるが、ADR 033 の判断（比較材料を作らない）を優先。必要になったら別 ADR で。

## 追補（2026-09-17）: 押したくなる言い回し・ワンクリック主ボタン・🔗 共有

### Context

運用 2 週間で「リアクションボタンが小さくて押しづらい・何をするボタンか分かりづらい」という声があった（ユーザー報告）。原因は 3 つ。

1. 入口が `👏＋` という 11px の点線ピル 1 つで、押すとまず絵文字ピッカーが開く（**2 クリック**）。
2. 絵文字の名前（いいね／ハート／拍手／スマイル／びっくり）はつぶやき向けの中立な語で、**作品に対して何を伝えたのかが言葉にならない**。
3. 「この作品が良い」を作品ページの外（つぶやき・Slack）へ持ち出す導線が無く、褒めが本人 1 人への通知で完結して連鎖しない。

### Decision

1. **主ボタンをワンクリックにする** — 「👏 ナイス！」を常時表示の主ボタン（カード 32px 高 / ライトボックス 46px 高）にし、押した瞬間に付く。残り 4 種は「＋」から**言葉つき**で選ぶ（カード）／全種を言葉つきで常時表示（ライトボックス）。
2. **作品ギャラリーだけ言い回しを変える。種別・絵文字・DB の値は変えない** — `utils/reactions.js` に `PORTFOLIO_REACTIONS` / `PORTFOLIO_LABEL` / `PORTFOLIO_PRIMARY` を追加。定義は引き続き 1 箇所（本 ADR 2 項の方針を維持）。マイ実績の合算（#1178）や通知の文面には影響しない。

   | 種別 | 絵文字 | つぶやき | 作品ギャラリー | ねらい |
   |---|---|---|---|---|
   | clap | 👏 | 拍手 | **ナイス！** | 万能の褒め言葉。主ボタン |
   | heart | ❤️ | ハート | **好き** | 好みに刺さった |
   | good | 👍 | いいね | **参考になる** | 自分の制作に活かしたい。お世辞でなく実利があるので押しやすい |
   | smile | 😊 | スマイル | **ほっこり** | 見ていて気持ちがいい |
   | surprised | 😳 | びっくり | **すごい…！** | レベルの高さへの驚き |

   「評価」ではなく「感想」の語を選んでいる。点数・優劣を含む語（最高／神／1位 など）は 4 項（順位化しない）に反するので使わない。
3. **押した手応えを返す** — 付けた瞬間にボタンがポンと弾み（`pf-pop`）、絵文字が浮かんで消える（`pf-float`）。外すときは静か。`prefers-reduced-motion` では動かさない（#1180 のナビと同じ配慮）。
4. **0 件のときは「最初の拍手をどうぞ 👏」** — ひとことの空状態（「最初のひとことをどうぞ」）と同じ言い回しで、一番乗りの動機を作る。ライトボックスのみ（カードはスペースが無い）。
5. **🔗 共有をライトボックスに置く** — 3 つの出口を持つ。
   - **💭 つぶやきで紹介する**: 本文（`👏 この作品、ナイス！` ＋ 作品名 ＋ 制作担当への `@メンション` ＋ 作品リンク）とサムネイルをセットした投稿モーダルを開く。投稿すると制作担当にはメンション通知が届き、つぶやきを見た全員が本文中の「🏆 作品を見る」チップからその場で作品を開ける。**褒めを本人 1 人への通知から、チーム全員が見る場所へ持ち出す**のがこの機能の役割。
   - **🔗 リンクをコピー**: ベル通知と同じディープリンク `/haruka.html?portfolio=<creative_id>`。Slack / Chatwork 用。
   - **📤 他のアプリで共有**: `navigator.share` がある端末（スマホ）だけ。
   - つぶやき本文の URL はこれまでリンク化されていなかった（メンション強調のみ）。本追補で `linkifyText` を通し、自アプリの作品リンクだけ「🏆 作品を見る」チップに置き換える（新規テーブル・列は増やさない。tweets に creative_id を持たせる案は見送り）。
   - 投稿モーダル（z-index 200）はライトボックス（1200）の下に隠れるため、紹介時はライトボックスを閉じてから開く。

### Consequences

- クリック数: 拍手 2 → 1。作品に対して「何を伝えたか」が言葉で残る。
- つぶやきに作品の紹介が流れると、そこからライトボックスが開き、さらに拍手が付く導線ができる（連鎖の入口）。
- 順位・件数比較は引き続き出さない（4 項）。「誰が押したか」の一覧も今回は出さない（別途検討）。
- `.pf-react` の高さがカードで約 20px → 32px に増える。130px 幅（スマホ）では主ボタン＋「＋」＋💬 が 2 行に折り返す。

### Alternatives

1. **絵文字を作品用に差し替える（🔥 💡 など）** — 見た目の新鮮さはあるが、マイ実績の合算（👍 に 👏 を合算）と通知アイコンの前提が崩れる。言葉だけ変える方が安全。
2. **tweets に `creative_id` 列を足して「作品つきつぶやき」にする** — リッチな埋め込みができるが migration と 3 段 PR が必要。まず本文リンク＋チップ化で様子を見る。
3. **カードにも 🔗 共有を置く** — 130〜330px のカード幅では主ボタン・＋・💬 で埋まる。ライトボックスは 1 クリック先なのでそちらに集約。
4. **「今月あなたが送った拍手 N 件」を本人だけに見せる**（自分の行動量の可視化・比較にならない）— 押す側の動機づけとして候補。今回は見送り、必要なら ADR 036 の枠で。

## 追補（2026-09-17）: 🎬 新着納品ショーケース — 納品された作品をホームで流し、その場で拍手する

### Context

納品はフロー上唯一の「達成」イベントだが、通知は本人（と案件の D/P）にしか届かず、チームの他のメンバーは
誰が何を仕上げたかを知る機会が無かった。作品ページ（🏆）は「探しに行く場所」であり、「開いたら目に入る場所」ではない。
本 ADR の拍手・ひとこと（#1141）と「🔗 つぶやきで紹介」（#1182）で**褒める道具**は揃ったので、
**褒める対象が自然に目に入る場**をホームに作る。

### Decision

1. **ホームに「🎬 新着納品」カードを置き、直近 7 日（JST）に納品された作品を 1 本ずつ送って見せる。** 全ロール共通の内容で、
   置き場だけ実効ロールで変える（作り手＝🏅 マイ実績の直下 / ディレクター＝👥 自チームの直下 / 管理層＝📢 全体連絡の前。ADR 015: `effectiveRole()`）。
   新着ゼロの週はカード自体を出さない。**ホームを開いた瞬間には自動再生しない**（作業の合間に開く画面で勝手に動くものを置かない・ADR 041 と同じ配慮）。
2. **「▶ スライドショー」で全画面オーバーレイにし、5 秒で次へ送る。** 下のパネルにマウスが乗っている間・動画再生中・リアクション操作直後は止める。
   ← → キー、スワイプ、⏭ スキップ、✕。リアクション行は本 ADR 追補（#1182）のライトボックス用 UI（`pfReactRowHtml` / `pfToggleReaction`・
   `PORTFOLIO_REACTIONS`）を **ctx を変えて関数ごと再利用**する（`pfItemsFor(ctx)` が作品配列を切り替える。二重実装しない）。
   💬 ひとことは既存ライトボックス（`pfOpenByCreativeId`）を開く。
3. **「誰が作ったか」を前面に出し、評価っぽい数字は一切出さない。** 表示は 作品 / クライアント・案件名 / 納品日 / 制作担当（納品時スナップショット
   `delivered_director_ids` ＋ `creative_assignments` の editor / designer / director_as_editor）/ 拍手・ひとこと件数 だけ。
   修正回数・遅延・単価・ランクは API（`GET /showcase`）が返さない（ADR 033「比較材料を作らない」と整合）。名前は id と表示名のみで、
   `users.avatar_url`（base64）は載せず既存の `/members/:id/avatar` を使う（#940）。
4. **既読は端末ローカル（localStorage）。DB には持たない。** `hfs_showcase_seen` に creative_id を配列で持ち、上限 500 件で古い順に捨てる。
   ヘッダーの「未見 N本」はこれで数える。畳み状態（`hfs_showcase_collapsed`）も同様。畳んでいても未見が増えたら
   ヘッダー行に「🎬 新着納品 N本」を太字で出す（中身は開かない）。ADR 041 の「最終閲覧は localStorage」と同じ判断で、
   端末が変わると既読が戻ることは許容する（端末間同期が欲しくなったら別 ADR）。
5. **同一案件 × 同一納品日（JST）で 4 本以上は 1 枚の「まとめスライド」にする**（純関数 `utils/showcase.js` の `bundleDeliveries()`。
   `TZ=UTC` / `Asia/Tokyo` の両方で jest 通過）。バナー一式のような一括納品を 12 枚連続で流さないため。タップで 1 本ずつ見られる。
   「👏 まとめてナイス！（N本）」は `POST /portfolio/reactions/bulk` で全本に `clap` を upsert（既に押していれば維持・外さない。上限 50 件）。
   制作担当への通知は**宛先 1 人につき 1 通に集約**し（「◯◯さんが「◯◯ バナー一式」12本にまとめて👏」）、
   同じ人 × 同じまとめ（案件 × 納品日 × 種別）は 24h に 1 回に抑える（単品の 3 項と同じ思想）。
6. **つぶやきへの自動投稿はしない。** 「納品されました」を自動でタイムラインに流すと、#1182 の「🔗 つぶやきで紹介」（人が選んで紹介する）と
   重複し、タイムラインが機械投稿で埋まってつぶやきの価値（人の気配）が薄れる。紹介したい人がスライドショーから 💬 → ライトボックス → 🔗 の
   経路で自分の言葉で流す形に留める。
7. **機密案件は `projects.showcase_hidden`（既定 false）で案件単位に除外する。** 案件編集モーダルの「🎬 ショーケースに出さない」チェック
   （既存の案件編集権限 `project.create_edit` に従う）。列未適用の環境では API が除外なしで動く（ホームを落とさない）。
   作品ページ（🏆）には影響しない（あちらは「探しに行く場所」で、案件の担当者が自分の作品を見られなくなる方が困る）。

### Consequences

- 納品作品が「誰が作ったか」つきでホームに並び、作った本人以外もその場で 👏 できる。褒めの入口が「通知を受けた本人」から「ホームを開いた全員」に広がる。
- `GET /api/haruka/showcase` は作品一覧 API の部品（`fetchPortfolioFilesByCreative` / `resolvePortfolioAspect` / `fetchPortfolioSocialMap`）を共用する。
  作品ページ側もこの共通化で同じ関数を使うようになった（挙動は不変）。
- 納品物ファイルが無い（外部リンクだけで納品された）作品は見せる絵が無いので流さない（作品ページの既定と同じ。件数は `no_file_count` で返す）。
- 新テーブル無し。migration は `projects.showcase_hidden` の 1 列のみ。
- 端末ごとに既読が独立する（ADR 041 と同じ許容）。

### Alternatives

1. **納品時に自動でつぶやきへ投稿する** — 6 項のとおり見送り。
2. **既読を `users` 列や専用テーブルに持つ** — migration と 3 段 PR が増えるわりに、「見た」の粒度は端末単位で足りる。ADR 041 と同じ判断。
3. **ホームを開いたら自動再生する** — 「開いたら勝手に動く」は Premiere / Photoshop から切り替えて来る作り手に嫌われる（ADR 041 の判断）。ボタンで始める。
4. **まとめスライドの閾値を 2〜3 本にする** — 同じ案件の 2〜3 本は個別に見ても負担が小さく、むしろ 1 本ずつ拍手したい。4 本以上を「一式」とみなす。

## 追補（2026-09-20）: 🎬 新着納品ショーケースの置き場をホームから「🏆 作品」ページへ移す

### Context

追補（2026-09-17）でホームに置いたフルカード（大サムネ＋サムネ列＋👏 行＋▶ スライドショー）は、ホームの縦幅を大きく取り、
マイフォーカス・つぶやき・全体連絡といった「今日やること」の手前で場所を奪っていた。一方で、作品を眺めて拍手する行為は
「🏆 作品」ページ（ギャラリー）の役割そのもので、👏 ナイス！・💬 ひとこと・🔗 共有もすべてそこにある。
ユーザーの決定で、**フルカードは作品ページの先頭に寄せ、ホームには 1 行の導線だけ残す**。API・DB・スライドショー本体は変えない。

### Decision

1. **作品ページ（`#page-portfolio`）の先頭に「🎬 新着納品」のフルカードを置く**（`#pf-showcase`、`renderShowcaseCard()`。全ロール同じ位置）。
   中身は 2026-09-17 のホームカードそのまま。「🏆 作品ページで見る」は同じページ上では意味が薄いので「🔍 大きく見る（ひとことも書けます）」に改め、
   既存の `pfOpenByCreativeId()` でライトボックスを開く（作品ページ上から呼ばれたときは一覧を読み直さず、今のフィルタに無ければ従来どおり全員・全件に広げて一度だけ探し直す）。
2. **ホーム（`#dash-showcase`）は 1 行の導線に縮める**: 「🎬 新着納品 この7日で N本（未見 M本） [🏆 作品で見る] [▶ スライドショー]」（`renderShowcaseLine()`）。
   ▶ スライドショーはホームからも全画面で開ける（オーバーレイ `#showcase-overlay` はページ外の共通要素）。置き場のロール分岐（作り手＝マイ実績の直下 /
   ディレクター＝自チームの直下 / 管理層＝全体連絡の前）は維持し、畳むボタンはホームには置かない。未見 0 なら「（未見 N本）」を出さない。新着ゼロなら行を出さない。
3. **ナビの「🏆 作品」に未見件数バッジ**（PC ナビ・ドロワーとも `.nav-unread-badge[data-for="portfolio"]`。つぶやきの未読バッジと同じ部品・同じ更新タイミング＝
   認証完了・タブ復帰・10 分間隔）。カード送り／スライドショーで見た瞬間（`scMarkSeen`）にも即時で減らす。「全部既読にする」ボタンは作らない
   （見れば減る・端末ローカル既読の思想は 2026-09-17 のまま）。
4. **`GET /showcase` の取得は `scFetchItems()` に 1 本化し、直近 60 秒の結果はキャッシュする。** カード・導線・バッジの 3 か所が同じ API を叩くため。
   配列は同じ参照を使い回し、`pfApplySocial` によるリアクション更新がキャッシュにも反映されるようにする。

### Consequences

- ホームが軽くなり、作品を眺める行為は作品ページに集まる。「🏆 作品」バッジが「見ていない納品がある」ことをホームに居なくても知らせる。
- サーバー・DB・migration は変更なし。`utils/showcase.js`・`routes/haruka.js` も不変。
- 既読（`hfs_showcase_seen`）・畳み状態（`hfs_showcase_collapsed`）のキーは変えないので、2026-09-17 版で見た記録は引き継がれる。

### Alternatives

1. **「🎬 新着納品」を独立メニューとして新設する** — 作品の置き場が「作品ページ・ホーム・新メニュー」の 3 つに割れ、ナビも 11 項目で過密になる。
   作品ページに寄せれば 👏 / 💬 / 🔗 の道具と同じ場所に揃う。不採用。
2. **ホームのフルカードを畳んだ状態で残す** — 畳んでいても縦幅とヘッダー行を取り、開けばまたホームが伸びる。1 行の導線とバッジで「気付ける」ことは足りる。不採用。
3. **バッジを「未見」でなく「今週の新着本数」にする** — 見ても減らない数字は通知として機能しない。つぶやきの未読バッジと同じ「見れば消える」にする。

## 追補（2026-09-23）: 🎬 スライドショーのパネルで 💬 ひとことをその場で読み書きする

### Context

スライドショー（全画面オーバーレイ）の下パネルには 👏 ナイス！と 4 種のリアクションがあり、拍手はその場で送れた。
一方 💬 ひとことは「ボタンを押す → スライドショーが閉じる → 作品ライトボックスが開く → そこで書く」という 3 段の導線で、
書き終えたあとスライドショーに戻る手段も無かった（追補 2026-09-17 の Decision 2 項）。
「褒める対象が目に入る場」で褒めの手数が拍手とひとことで揃っていないのは不自然で、ユーザーから「ここでコメントをダイレクトに入れたい」と指摘があった。

### Decision

1. **パネルの操作面を 2 カラムにし、右側に 💬 ひとこと欄（一覧＋入力）を常設する。** 左は従来どおり 👏 ナイス！＋4 種のリアクション。
   ひとこと欄は作品ページ／ライトボックスと同じ部品（`pfCommentsHtml` / `pfSubmitComment` / `pfDeleteComment`）を **ctx `'sc'` で再利用**する
   （`pfItemsFor(ctx)` が `scFlat` を返す。二重実装しない・追補 2026-09-17 のリアクション行と同じ流儀）。
   本文はスライドを表示した時点で `GET /portfolio/:id/comments` を 1 回取りに行き、`pfCommentsCache` に載せる（ライトボックスと共有）。
   ライトボックスへ飛ぶ `scOpenComments()` は廃止。
2. **入力中は自動送りを止める。** マウスホバーでの停止はスマホに無いので、ひとこと欄の `focusin` / `focusout` で `scSlide.typing` を立て、
   さらに打ちかけの文字が残っている間（`scHasCommentDraft()`）はフォーカスが外れていても送らない（5 秒後に再判定）。
   送信直後は `scResetTimer()` で仕切り直し、フォーカスを入力欄に戻す（続けて書ける）。
3. **取得完了や件数更新でパネル内の欄を差し替えるとき、打ちかけの文字とフォーカスは引き継ぐ**（`pfRerenderCommentsPanels` の sc 分岐）。
   送信成功時だけ先に入力欄を空にしてから差し替える。
4. **一覧は最大 132px（スマホ 96px）でスクロール。** パネルは `max-height: 44vh` なので、ひとことが増えてもステージ（作品）の面積を奪わない。
5. **キー操作の干渉を避ける。** 入力欄の `keydown` は `stopPropagation`（← → Space がスライド操作に流れない）。Esc は入力欄から
   フォーカスを外すだけにし、もう一度 Esc でスライドショーを閉じる（書きかけを Esc 一発で失わない）。

### Consequences

- 拍手とひとことがスライドショーの同じパネルで完結する。ライトボックス側の 💬 欄・作品カードの 💬 開閉は不変（同じ関数の ctx 分岐が増えただけ）。
- API・DB・通知は変更なし（ひとことの投稿は既存 `POST /portfolio/:id/comments`。制作担当への通知も既存のまま）。
- スライドごとにひとこと取得が 1 リクエスト増える（未キャッシュの作品のみ。自動送り 5 秒間隔なので負荷は軽微）。

### Alternatives

1. **💬 ボタンを押したときだけ欄を開く（作品カードと同じ開閉式）** — 開く 1 手が残り「ダイレクトに入れる」にならない。パネルは横幅があるので常設で困らない。
2. **ライトボックスをスライドショーの上に重ねて開く（閉じずに）** — 全画面の上に別の全画面が乗る二重モーダルになり、戻る導線と自動送りの扱いが複雑。
3. **パネル内に独自の簡易フォームを新設** — 削除権限（`can_delete`）・名前表示（NameDisplay）・キャッシュ反映を二重に持つことになる。既存部品の ctx 化で足りる。
