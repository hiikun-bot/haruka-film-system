# ADR 051: 案件への参加は、メンバー本人が P・D・管理者のうち宛先を選んで理由つきで申請し、承認ボタンで支払先メンバーに登録する

- Status: Accepted
- Date: 2026-10-13
- Related: ADR 002（成果物グループ＝`project_estimate_lines` / 支払先 `project_estimate_line_costs`）, ADR 015（VIEW AS チェックリスト）, ADR 028（作業時間報告）, ADR 037（単価の承認）, ADR 048（新テーブルは RLS 有効化）, ADR 049 §7（個別通知は共有ルームに流さない）

## Context

メンバー（編集者・デザイナー等）が案件に参加したいとき、今は本人には登録手段が無く、さとるさんやプロデューサーなど登録権限のある人へ別経路（Chatwork 等）で頼み、頼まれた側が案件編集を開いて支払先メンバーを追加している。依頼が埋もれたり、誰に頼めばよいか分からなかったりする。

さとるさんの指示（2026-10-13）:
- 案件に含まれるディレクター・プロデューサー・管理者に対して、メンバー側から参加申請を出せるようにする
- 申請者は権限がない人
- 申請時に誰宛てに送るか（D・P・管理者）を選べる。理由の記載は必須

HFS には「案件メンバー」という単一のテーブルは無い。案件にお金と作業時間でひもづくのは成果物グループの支払先（`project_estimate_line_costs.user_id`）で、作業時間報告（ADR 028）の「自分の案件」判定や案件別作業時間の閲覧権（`/work-hours/project-summary`）もこれを見ている。

## Decision

### 1. 申請は専用テーブル `project_join_requests` に持つ

`project_id` / `requester_id` / `recipient_ids UUID[]`（選んだ宛先・1 人以上）/ `message`（理由・必須）/ `status`（pending → approved / rejected / cancelled）/ `decided_by` / `decided_at` / `decision_note` / `created_line_cost_id`。同じ人が同じ案件に申請中を 2 件持てない（部分 UNIQUE）。RLS 有効（ADR 048）。

通知ログ（`notification_logs`）に状態を持たせない。承認・却下の状態遷移と「誰が決めたか」を残す必要があるため。

### 2. 申請できるのは「その案件の支払先を登録する権限が無い人」

実効ロールで `project.create_edit` も `project.pricing_edit` も持たない人（既定では editor / designer / external_director）。権限のある人には申請ボタンを出さず、API も 400 で「直接登録できます」と返す。すでにその案件の支払先に入っている人も 409。

### 3. 宛先の候補は「その案件の P・D ＋ 管理者（admin）」。申請者が 1 人以上選ぶ

- 候補 API がサーバー側で組み立て、申請 API は候補外の宛先を弾く（任意の人に通知を飛ばせないように）
- 既定では案件の P・D にチェック（未設定なら管理者）
- 宛先に選ばれた人だけに通知する（管理者全員には撒かない）

### 4. 承認は「宛先に選ばれた人」または管理者。承認と同時に支払先メンバーへ登録する

承認モーダルで **成果物グループ・役割・課金方式・単価** を入れて「承認して登録」を押すと、既存の支払先追加（`POST /projects/:id/lines/:line_id/costs`）と同じ処理で `project_estimate_line_costs` に 1 行入る。

- 承認者にも支払先登録の権限（`project.create_edit` か `project.pricing_edit`）が必要。権限が無い宛先（例: 権限を外されたディレクター）は承認できない
- ADR 037 の単価承認はそのまま効く。管理者以外が承認・登録した単価は成果物グループが「承認待ち」になり、管理者へ通知される
- 支払先を別の方法で入れた／単価がまだ決まらない場合のために「登録せずに承認」も選べる（`created_line_cost_id` は NULL）
- 却下は理由（任意）を添えられる。申請者は申請中なら自分で取り下げられる

### 5. 通知は通知ベル＋個別 DM。共有ルームには流さない

- 申請時: 宛先それぞれへ通知ベル（種別 `project_join_request`）＋ `notifyMember(..., { privateOnly: true })`（ADR 049 §7）。申請理由を本文に載せる
- 承認・却下時: 申請者へ同じ種別で結果を通知
- 本人の受信設定では止めない（ADR 043 §3。止めると申請が誰にも届かず業務が止まる）。CATALOG に出さないので migration での設定列追加もしない
- リンクは `/haruka.html?join_request=<id>`。宛先が開くと承認モーダル、申請者が開くと案件タブで状況が見える

### 6. 画面

- 案件タブの各案件行に、申請できる人には「🙋 参加申請」、申請中なら「申請中」チップ（クリックで取り下げ）
- 承認できる人には、案件タブ上部に「📨 参加申請が N 件届いています」の帯と案件行のバッジ。どちらからも承認モーダルを開ける

## Consequences

- 新テーブル 1 つ（migration → 本番適用 → コード PR の順。ADR 048 の RLS も同ファイル）
- 支払先登録の本体は既存 API の処理を関数化して共用する。単価承認（ADR 037）・UNIQUE 制約（同じロール×担当者は 1 行）の挙動は変わらない
- 申請の監査（誰がいつ承認・却下したか）は `project_join_requests` に残る

## Alternatives

- **申請＋通知だけにして、登録は承認者が案件編集で行う**: 登録の手間が残り、目的（手間をなくす）を満たさないので不採用。「登録せずに承認」として逃げ道だけ残す
- **クライアントの担当チームに加入させる**: 担当者候補の初期チームが変わるだけで、支払・作業時間報告とつながらないので不採用
- **管理者全員＋P層全員に一斉通知**: 宛先を本人が選ぶという指示に反し、関係ない人に通知が積もるので不採用
